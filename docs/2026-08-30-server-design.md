## 0. 결론 요약

- **서버는 두 가지만 한다**: ① 사용자가 수기 등록한 제품명을 익명으로 모아 다른 사용자의
  자동완성에 제공(크라우드소싱 제품 DB — 식약처 밖 비기능성 커버리지의 유일한 해법, 리서치
  결론의 실행) ② 제품·관찰 기록의 백업·복원(기기 이전 시 데이터 전멸 사고의 예방).
- **불변식: 사진 바이트는 서버에 절대 올라가지 않는다**(사용자 결정). `LOCAL_ONLY`
  문장(「사진은 이 기기에만 저장되며 어디로도 전송되지 않습니다」)이 글자 그대로 계속
  참이어야 한다 — 검수 통과 문구이자 온보딩 고지다. 서버는 페이로드 상한 + 재귀 문자열
  길이 상한으로 이 불변식을 구조적으로도 막는다(§4-2). 대가는 정직하게 진다: **기기를
  바꾸면 사진은 여전히 사라진다** — 복원 화면이 이를 복원 **전에** 말한다(§3-4).
- **사용자 식별 = `User.getAnonymousKey()`의 hash를 소유 증명 토큰(capability)으로 쓴다.**
  로그인·개인정보 수집 0. 핵심 미검증 가정(기기를 바꿔도 같은 토스 계정이면 같은 hash인가)은
  실기기 2대 검증 절차를 단계에 박고(§3-1·v3-2), 실패 시 폴백(복원 코드 → appLogin)을
  설계에 미리 세워 둔다.
- **동기화가 아니라 백업·복원이다.** 전체 상태 블롭(제품+관찰, 수십 KB)을 LWW로 덮어쓴다 —
  기기 1~2대·단일 사용자 데이터에 증분 동기화·CRDT는 YAGNI(§3-3). 서버가 죽어도 앱은
  v2와 동일하게 돈다 — 모든 서버 경로가 무음 폴백이다(기존 규율 계승).
- **크라우드소싱 데이터는 이름·브랜드 명사뿐이다.** 효능·기능성 정보는 사용자 입력에서 받지도
  보여주지도 않는다 — 「식약처 보고정보의 인용」이라는 법적 방패(v2-2 §3-4)를 사용자 데이터가
  오염시키지 않게 축을 분리한다. 노출은 **서로 다른 2인 이상 등록**부터(§3-5), 화면은 출처를
  구분한다(뱃지는 mfds 전용 유지).
- **호스팅은 이미 돌고 있는 BookTimer의 EC2(t3.small·서울)에 동거하고, 그 안의 MySQL 8.4를
  재사용한다**(사용자 결정 2026-09-01 — AWS 실측 §2-5가 전제를 뒤집었다). **추가 비용 0원**이고,
  초안이 만들려던 것(인스턴스·Elastic IP·보안그룹·IAM 역할·nginx·certbot·Postgres·swap·
  부트스트랩 스크립트)이 **전부 사라진다** — 리버스 프록시가 **Caddy**라 HTTPS가 자동이기
  때문이다(초안의 「최대 함정」이 소멸). 남는 것은 Caddy 블록 3줄 · MySQL 데이터베이스 1개 ·
  A 레코드 1개 · 컨테이너 1개뿐. 대가는 **메모리 공유 하나**이고, 컨테이너 `mem_limit`이
  「facefit이 죽어도 BookTimer는 산다」를 보장한다(§3-6). 되돌리는 길(**분리 경로**)은
  §3-6-1에 절차·신호·사전 준비까지 적어 두었다. 레포는 모노레포(`server/` 신설 — §3-7).
- **첫 조각은 백업이다**(v3-1). 표면이 가장 작고(테이블 1·엔드포인트 3), 인증 가정을 가장
  먼저 실전 검증하며, 콘텐츠 품질 문제가 없다. 크라우드소싱은 그 위에 얹는다(v3-3).
  클라우드 OCR 프록시는 이번 범위 밖 — 같은 Spring 앱에 컨트롤러로 얹을 여지만 남긴다(§7).

## 1. 목표 · 비목표

**목표**: ① 수기 등록 제품의 익명 수집 + 다른 사용자 자동완성 제공(출처 구분 포함)
② 제품·관찰 기록의 옵트인 백업과 기기 이전 복원 ③ 서버가 죽거나 느려도 앱이 v2와 동일하게
도는 무음 폴백 ④ 월 0원 운영. 그것뿐이다.

**비목표(YAGNI — §7 보류 목록에 이유)**: 사진 백업(불변식 — §3-2) · 클라우드 OCR 프록시 ·
실시간 동기화/멀티 디바이스 동시 편집 · 로그인(appLogin) · 관리자 웹 UI · 크라우드소싱
데이터의 검수·큐레이션 조직 · 푸시 발송 서버(콘솔이 담당 — v2-1) · 사진 앨범 내보내기
(클라 전용 별도 계단 — §3-2·§7).

## 2. 전제 · 실측

### 2-1. 왜 서버까지 왔나 (이번 세션 실측 — OCR 무료 경로 전멸)

원 문제는 「화장품 이름이 너무 길어 손으로 못 친다」였고, 사진에서 글자를 뽑는 무료 경로를
실기기(iOS 18+)에서 전부 재고 전멸을 확인했다:

- 앱인토스 SDK에 OCR·텍스트인식·바코드 API **없음**(export 전수 확인).
- 앱 안에서 찍은 사진을 `<img>`로 띄우고 롱프레스 → 상호작용 자체가 없음. 같은 사진을
  아이폰 사진 앱에서 열면 라이브 텍스트 정상 → **토스 웹뷰가 막은 것**(우리 CSS엔
  `user-select:none`·`-webkit-touch-callout:none` 없음 — 앱 결함 아님).
- 입력칸 롱프레스 콜아웃은 정상(붙여넣기·자동 완성)인데 **「텍스트 스캔」 항목만 없음** —
  WKWebView 웹 편집 영역엔 그 항목이 안 붙는다.
- iOS엔 카메라 앱을 여는 공개 URL 스킴이 없고, SDK `Device.openCamera`·`<input capture>`는
  사진을 웹뷰로 되돌려줘 같은 막다른 길. 음성 입력은 사용자 기각(재시도 UX 불량).

남은 두 길이 이 서버의 두 목적이다: **다른 사용자가 이미 친 이름을 재사용**(크라우드소싱)하거나,
**클라우드 OCR**(서버 필수 — 이번엔 여지만, §7). 커버리지 리서치(2026-08-30)는 업계 선두조차
운영 프로세스(수작업+제보)로 DB를 만든다는 것을 확인했다 — 개인 프로젝트가 가질 수 있는
등가물은 사용자 등록의 집합뿐이다.

### 2-2. SDK 실측 — 사용자 식별 재료

- `User.getAnonymousKey()` → `{ type: 'HASH', hash }`. 문서상 「미니앱에서 **사용자의**
  고유 키」 — 기기 키 `getDeviceId()`와 **별개 API**다(사용자 축임을 시사). 토스 5.232.0+.
- `TossAuth.login()`(appLogin) → `{ authorizationCode, referrer }`, 「서버로 전달해야 한다」 —
  서버가 생긴 지금은 쓸 수 있으나 **콘솔 토스로그인 설정 + 약관 + 개인정보 수집 동의**가
  붙는다(수집 0 원칙의 포기). 폴백 최후순위로만 둔다(§3-1).
- **핵심 미검증 가정**: hash가 **기기를 바꿔도 같은 토스 계정이면 동일**한가. 문서는
  「사용자의 키」라 하지만 실측 전엔 못 믿는다 — 검증 절차와 실패 폴백을 §3-1에 세운다.
- 미지원 토스 버전에서 SDK 호출이 던질 수 있다 — notify.ts 전례(`isSupported`가 토스 밖
  전역을 읽어 TypeError)와 같은 급으로 래퍼가 try로 삼키고, 미지원이면 백업 UI 자체를 숨긴다.

### 2-3. 현 저장 실태 (백업 대상의 크기)

| 데이터 | 위치 | 크기 실측/산정 | 백업 |
|---|---|---|---|
| 사진 | IndexedDB `facefit-photos` | 장당 100~200KB · 365장/년 ≈ 최대 70MB | **✕ 불변식(§3-2)** |
| 제품 | localStorage `facefit.products` | 상한 200건 × ~0.5KB(mfds 스냅샷 포함) ≤ ~100KB | ○ |
| 관찰 | localStorage `facefit.notes` | 날짜당 ~25B × 365/년 ≈ ~10KB/년 | ○ |
| 온보딩·알림 플래그 | localStorage | 수 B | ✕ — 기기 로컬 UX 상태다. `notifyPrompted`를 복원하면 새 기기에서 알림 제안이 부당하게 억제된다 |

**백업 페이로드는 수십 KB급이다** — 사진을 뺀 순간 동기화 문제의 난도가 한 계단 내려간다.
전체 블롭 덮어쓰기(§3-3)가 성립하는 근거다.

### 2-5. AWS 실측 (2026-09-01 · CLI 직접 조회 — 설계 전제 2개를 뒤집었다)

> 근거: `aws sts get-caller-identity` · `ce get-cost-and-usage` · `ec2 describe-instances` ·
> `cloudwatch get-metric-statistics` · SSM Run Command(`free -m` · `docker ps` · `docker stats`).

**① 프리티어가 없다(확정).** 6·7·8월 청구에서 `UnblendedCost`와 `NetUnblendedCost`가 완전히
같다 — **크레딧이 0원 적용**됐다는 뜻이다. 8월 실결제 **$32.80**. 「프리티어 잔여를 쓴다」는
초안 전제(§3-6 구판)는 성립하지 않는다. 신규 t3.micro는 첫 달부터 **월 ~$15.9**.

**② 서울에 인스턴스가 이미 돌고 있다.** `i-07a649585c25707a3`(Name=`booktimer`) ·
**t3.small** · Amazon Linux · Elastic IP `15.165.95.129` · gp3 30GB · SSM 에이전트 **Online** ·
크레딧 모드 `unlimited`.

**③ 계정 구조** — 관리자는 CLI 프로필 **`booktimer`**(계정 `459338751419`)뿐이다.
`default` 프로필은 **다른 계정**(`681689809064`)의 `github-actions` CI 사용자라 Route 53·S3·
IAM·SSM이 전부 권한 거부다. ⚠️ **facefit 관련 AWS 명령은 전부 `--profile booktimer`**를 붙인다.
`booktimer.app`은 Route 53 호스팅 영역 **`Z0795663J1W7C48SU27B`**(같은 계정)에 있다 —
초안의 「DNS 관리 위치 미확인」이 해소됐다.

**④ 자원 여유는 비대칭이다.**

| 자원 | 실측 | 판정 |
|---|---|---|
| CPU | 7일 평균 **1.8~2.2%**, 크레딧 **576/576 만점 고정**(한 번도 안 깎임) | 남아돈다 |
| 디스크 | 30GB 중 **24GB 여유** | 남아돈다 |
| 메모리 | 1,913MB 중 **available 910MB**, swap 2GB 중 653MB 사용 | **빠듯하다** |

**⑤ 실행 스택은 Docker다.** 호스트에 nginx도 `/etc/letsencrypt`도 **없다**.

| 컨테이너 | 이미지 | `mem_limit` | 실사용 |
|---|---|---|---|
| `booktimer-app-green-1` | ECR `booktimer:latest`(8080) | 700MB | 428.6MB (61%) |
| `booktimer-caddy-1` | **`caddy:2-alpine`**(80·443 점유) | 128MB | 27.1MB (21%) |
| `booktimer-mysql-1` | **`mysql:8.4`**(3306) | 600MB | 240.1MB (40%) |

이 표가 §3-6의 결정을 통째로 만들었다 — **Caddy**(HTTPS 자동 → certbot 설계 소멸) ·
**MySQL**(Postgres 전제 폐기) · **컨테이너별 상한 관행**(격리 수단이 이미 있다) ·
**ECR + `app-green` 네이밍**(배포 패턴을 새로 만들 필요 없음).

⚠️ **미확인**: BookTimer의 compose 파일·Caddyfile 위치와 내용(`import` 지시어 사용 여부)은
아직 안 봤다 — §3-7·§6 태스크 3의 선행 확인 항목이다.

## 3. 결정 사항 (대안 비교)

### 3-1. 사용자 식별·호출자 인증 — 익명 키 = 소유 증명 토큰 ✅

| 대안 | 개인정보 | 검수·콘솔 작업 | 기기 이전 | 판정 |
|---|---|---|---|---|
| **A. `getAnonymousKey().hash`를 capability 토큰으로** | 0(익명 해시) | 0 | **가정 성립 시** 자동 — 새 기기에서 같은 키로 복원 | ✅ **채택.** 로그인 화면·약관·수집 동의 전부 불필요. 가정 검증은 v3-2(아래) |
| B. `TossAuth.login()`(appLogin) | 수집 발생(약관·동의 필수) | 콘솔 토스로그인 설정 + 개인정보 문구 전면 개정 | 확실 | 기각(보류) — 수집 0 원칙을 깨는 비용이 크다. **A의 가정이 깨지고 복원 코드도 부족할 때의 최후 폴백**으로만(§7) |
| C. 자체 발급 랜덤 키(첫 실행 시 생성) | 0 | 0 | ✕ — 키가 기기에만 있어 기기 이전이 원천 불가(백업의 존재 이유 부정) | 기각 |

**A의 인증 모델**: 키를 아는 자 = 소유자다(capability). 서버는 키를 검증할 방법이 없고
(토스에 익명 키 검증 API가 없다 — 미확인이면 가정으로 §8에 등재), 검증할 필요도 없다 —
키가 고엔트로피 해시라면 추측 불가이고, 제시된 키의 백업만 돌려주므로 남의 데이터에 닿을
수 없다. 서버는 원 키를 저장하지 않는다 — **sha256(키)를 PK로** 저장해 DB 유출 시에도
원 키(=열람 토큰)가 새지 않게 한다(§4-2).

**공개 API가 되는 문제(호출자 인증)**: 서버가 열리면 누구나 부를 수 있는 무료 API다.
번들에 앱 토큰을 심는 것은 MFDS 키와 같은 「추출 가능한 장식」이라 **안 한다**(보안 연극 —
진짜 방어는 아래 셋이다):

1. **레이트리밋** — IP당·키당 상한(§4-2). 단일 인스턴스 전제의 인메모리 고정 창이면 족하다.
2. **피해 상한 분석** — 최악의 어뷰즈 = 가짜 키 대량 생성으로 백업 저장 폭탄. 키당 1블롭 ×
   512KB 상한 + 디스크가 고정 크기 EBS 30GB라 **비용 폭발이 구조적으로 불가능**하다
   (가득 차면 쓰기가 실패할 뿐이고, 그날 앱은 백업만 무음 연기된다 — v2-2 쿼터 소진과 같은
   등급. 종량 과금 스토리지가 아니라는 것이 이 상한의 핵심이다). 크라우드소싱 오염은
   노출 기준 2인(§3-5)이 막는다.
3. **관측** — 키 수·저장량 주간 확인(§5). 어뷰즈가 실측되면 그때 앱 토큰·챌린지를 단다.

**미검증 가정의 검증 절차(v3-2 — 사용자 실기기 몫)**: 백업 화면에 키 지문(sha256 앞
6자리)을 상시 표시한다(무해·6자리라 역산 불가). ① 본 기기에서 지문 기록 → ② 두 번째
기기(공기계 등)에 토스 설치·같은 계정 로그인 → ③ 콘솔 QR 테스트로 앱 실행 → ④ 지문 대조.
동일하면 가정 확정, 다르면 아래 폴백 사다리를 밟는다. ⚠️ 토스가 기기 이전 시 옛 기기를
로그아웃시킬 수 있다 — 검증 후 본 기기 재로그인을 감수한다(1회성).

**폴백 사다리(가정이 깨졌을 때 — 지금 만들지 않는다, 설계만 세워 둔다)**:

| 계단 | 방식 | 커버 | 비용 |
|---|---|---|---|
| 1. 복원 코드 | 옛 기기에서 「이전 코드 만들기」 → 서버가 8자 코드 발급(24h 유효, 1회용) → 새 기기에서 코드 입력 → 그 백업에 연결 | 기기 이전(옛 기기 생존 시) | 테이블 1·엔드포인트 2 — 로그인·개인정보 여전히 0 |
| 2. appLogin | 토스 로그인으로 계정 귀속 | **폰 분실**까지 | 약관·수집 동의·콘솔 설정 — 최후 수단 |

⚠️ 가정이 깨지고 폰도 분실이면 복원 코드로도 못 돌아온다 — appLogin 없인 커버 불가.
이 잔여 구멍은 §8에 명시하고, 가정 검증 결과가 나온 뒤에 계단 승격을 판단한다.

### 3-2. 백업 범위 — 메타만 (사용자 결정으로 고정) ✅

| 대안 | `LOCAL_ONLY` 문장 | 페이로드 | 개인정보 무게 | 판정 |
|---|---|---|---|---|
| ① 사진 포함 전체 백업 | **거짓이 된다** — 검수 통과 문구·온보딩 고지 동시 파기. 재검수 리스크 최대 | ~70MB/인 | 얼굴 사진 = 민감 축(유출 시 회복 불능). 암호화·보존·삭제 의무가 통째로 생긴다 | 기각 |
| **② 메타만(제품·관찰)** | **글자 그대로 계속 참** — 사진은 이 기기에만 | 수십 KB/인 | 익명 키에 묶인 제품명·날짜뿐 — 이름·연락처 0 | ✅ **채택(사용자 결정)** |
| ③ 사진 옵트인 | 옵트인 화면에서만 조건부 참 — 「어디로도 전송되지 않습니다」에 각주가 달리는 순간 문장의 힘이 죽는다 | 가변 | ①과 동일한 의무가 옵트인 인원만큼 발생 | 기각(보류) — ②가 돌아간 뒤 수요가 실측되면 별도 설계로 |

**불변식(이 설계의 제1 규칙): 사진 바이트는 어떤 경로로도 서버에 올라가지 않는다.**
클라이언트는 백업 페이로드에 사진을 넣을 코드 자체가 없고, 서버는 ① 요청 본문 512KB 상한
② **재귀 문자열 길이 상한 2,000자**(사진 1장의 base64 ≈ 27만 자 — 구조적으로 불가)로
밀반입을 이중 차단한다(§4-2). 이 불변식을 어기는 변경은 `LOCAL_ONLY` 문구·온보딩 고지·검수
이력을 동시에 거짓으로 만든다 — 코드 리뷰가 지켜야 할 한 줄이다.

**정직한 구멍**: 기기를 바꾸면 **사진은 여전히 사라진다**. 백업이 지키는 것은 「무엇을 언제
썼고 그날 어때 보였나」(제품 기간 + 관찰)이고, 타임랩스의 재료(사진)는 못 지킨다. 복원
화면이 이를 **복원 전에** 명시한다(§3-4 — 복원하고 나서 알게 되면 사고다). §8 리스크에도 박는다.

**보완책 — 사진은 사용자 손으로**: 서버 대신 **기기 안에서의 이동** 경로를 별도 계단으로 둔다.

| 후보 | 평가 |
|---|---|
| **A. SDK `Device.saveBase64Data` 반복 호출(앨범 저장)** | **권고 후보.** SDK 공식 경로 · 전송이 아니라 기기 내 이동이라 불변식 무관 · 앨범에 들어간 사진은 iCloud/구글포토가 알아서 이어 준다(우리가 안 만든 백업 인프라를 사용자가 이미 가졌다). 미검증: 365회 반복 호출의 rate·권한 UX(§8) |
| B. `navigator.share` 파일 공유 | 웹뷰 파일 공유 지원 미실측 + 1회 다중 파일 상한 불명 — 이번 세션의 웹뷰 실측(라이브 텍스트 차단 등) 정황상 도박이다 |
| C. zip `<a download>` | iOS 웹뷰 다운로드는 신뢰 불가(전례) — 기각 |

이건 서버와 무관한 클라 전용 계단이라 **v3 범위 밖으로 미룬다**(§7 — v3와 독립·병행 가능).
근거: 서버 도입이 이번 계단의 임계 경로이고, 내보내기는 언제 얹어도 값이 같다.

### 3-3. 동기화 프로토콜 — 전체 블롭 백업·복원(LWW), 동기화 아님 ✅

이름부터 정직하게: **백업·복원이지 동기화가 아니다.** 시나리오는 「기기 이전」(사용자 결정)
하나이고, 두 기기 동시 사용·병합은 범위 밖이다.

| 대안 | 판정 |
|---|---|
| **A. 전체 상태 블롭 PUT(LWW — 마지막 쓰기 승리)** | ✅ **채택.** 페이로드가 수십 KB(§2-3)라 매번 전체를 보내도 싸다. 삭제·수정·추가가 전부 「다음 PUT이 곧 진실」로 수렴 — 삭제 마커·부분 실패·머지 코드가 0줄 |
| B. 증분 동기화(변경분 diff + 삭제 마커) | 기각 — 충돌 해소·순서 보장·묘비(tombstone) 관리가 생기는데, 얻는 것은 수십 KB의 절약뿐. YAGNI |
| C. 레코드 단위 동기화(제품별 버전) | 기각 — B와 같은 이유 + 클라 저장 구조(배열 통째 저장)와 어긋난다 |

프로토콜 규칙(§4-2에 API로 구체화):

- **업로드**: `saveProducts`/`saveNote` 뒤 5초 디바운스로 전체 블롭 PUT — fire-and-forget.
  실패하면 `facefit.backupDirty` 플래그만 세우고 **다음 앱 시작 시 재시도**(무한 재시도
  루프·백오프 코드는 안 만든다 — 앱을 여는 행위가 곧 재시도 트리거다).
- **충돌**: 서버는 무조건 덮어쓴다(LWW — 서버 수신 시각 기준). 기기 1~2대 전제에서 충돌의
  실체는 「이전 직후 옛 기기가 한 번 더 쓰는」 경우뿐이고, 피해 상한은 메타 며칠치 —
  `clientSavedAt`을 블롭에 실어 복원 미리보기에 시점을 보여주는 것으로 족하다.
- **삭제**: 블롭 덮어쓰기가 자연 처리. 「백업 끄기」는 DELETE(서버 데이터 즉시 삭제 —
  삭제권 이행이자 문구 신뢰의 근거).
- **부분 실패**: 블롭이 원자 단위라 존재하지 않는다 — 성공 아니면 통째 실패(재시도).
- **용량 상한**: 요청 본문 512KB(제품 200건 상한 × ~1KB + 관찰 수년치에 8배 여유).
  초과는 400 — 클라가 만들 수 없는 크기라 사실상 어뷰즈 신호다.
- **복원**: 수동 트리거만(§3-4). 자동 복원은 안 한다 — 빈 로컬 상태는 신규 사용자의 정상
  상태이기도 해서, 자동이면 「새로 시작하고 싶은」 사용자의 의사를 덮는다.

### 3-4. 백업 UX — 옵트인 제안 1회 + 상시 버튼, 복원은 온보딩에서 ✅

| 결정 지점 | 채택 | 기각 대안과 이유 |
|---|---|---|
| 켜는 방식 | **옵트인** — 서버 전송이 처음 생기는 기능이라 사용자 행위로 시작한다. 검수·문구 관점에서도 「켜면 전송」이 「기본 전송」보다 설명이 한 문장 짧다 | 기본 켜짐 — 고지 없이 전송이 시작되는 모양새. 수집 0으로 통과해 온 앱의 신뢰 축을 흔든다 |
| 제안 동선 | v2-1 푸시와 같은 패턴 — **의미 있는 순간에 1회 제안**(제품 첫 등록 완료 직후: 「기록이 쌓이기 시작했어요. 기기를 바꿔도 잃지 않게 백업할까요?」) + **Home 상시 버튼**(멱등). `backupPrompted` 플래그로 재제안 억제(notifyPrompted와 동형) | 설정 화면 신설 — 설정 화면 자체가 없는 앱이다. 버튼 하나에 화면 하나는 과하다 |
| 복원 동선 | **온보딩 화면 하단 링크** 「기기를 바꿨나요? 기록 복원」 — 새 기기의 첫 화면이 온보딩이라 여기가 유일하게 자연스러운 자리다 | Home 버튼 — 온보딩을 넘긴 뒤라 「이미 새로 시작한」 상태와 섞인다 |
| 복원 화면 | GET → 미리보기: 「제품 n건 · 관찰 m건 (yyyy-mm-dd 저장분)」 + **「사진은 복원되지 않아요 — 사진은 이전 기기에만 저장돼 있어요」를 확인 버튼 위에 고정 표기** → 확인 시 로컬 덮어쓰기 | 복원 후 안내 — 사고다(§3-2 정직한 구멍을 사후에 알리는 꼴) |
| 미지원 토스 버전 | `getAnonymousKey` 래퍼 try 실패 시 백업 제안·버튼 **자체를 숨긴다**(notify 전례) | 에러 안내 — 사용자가 할 수 있는 일이 없는 안내는 소음 |

### 3-5. 크라우드소싱 — 명사만 · 2인 노출 · 출처 구분 ✅ (수집 방식은 사용자 결정 2026-09-01)

**수집**: 사용자가 **수기로**(mfds 스냅샷 없이) 저장한 제품의 `name`(+있으면 사용자가 아는
브랜드는 없다 — 이름뿐)을 저장 시 익명 전송한다(fire-and-forget · 실패 무음). mfds 부착
제품은 보내지 않는다 — 식약처에 이미 있는 것을 모을 이유가 없다.

| 결정 지점 | 채택 | 기각 대안과 이유 |
|---|---|---|
| 수집 방식 | **수기 저장 시 자동 전송 + 고지**(온보딩·콘솔 상세설명에 「직접 등록한 제품 이름은 익명으로 모아 다른 사용자의 검색에 쓰일 수 있어요」) — 제품명은 개인정보가 아니고, 기여량이 곧 이 기능의 생사다 | 등록 폼 체크박스 — 기여율이 죽는다(폼에 개입이 늘수록 수기 등록 흐름 훼손). 별도 「제공하기」 버튼 — 두 단계 조작, 같은 이유 |
| 노출 기준 | **서로 다른 익명 키 2인 이상 등록**부터 검색에 노출 | 1인 — 오타·사적 메모(「엄마 크림」)·장난이 그대로 전체 노출. 3인+ — 현 사용자 규모에서 영영 노출 0(콜드 스타트 사망). 2인은 「서로 다른 두 사람이 같은 문자열을 쳤다」는 최소한의 실재 신호다 |
| 중복 병합 | 정규화 키 = 공백 제거 + 소문자화(v2-3 `norm`과 같은 규칙 — 클라·서버가 같은 술어) · 표시 문자열은 **최초 등록 원문** | 편집거리 병합·표기 교정 — 사전 없이 하면 오병합이 더 위험. YAGNI |
| 신고·차단 | 제안 롱프레스 등 UI는 안 만들고 **서버에 신고 엔드포인트 + hidden 플래그**만 둔다. 운영자(=사용자 본인) 처리는 SQL 직접 — 관리자 UI는 YAGNI | 자동 금칙어 필터 — 목록 관리가 낡는 속도 > 효용. 2인 기준 + hidden으로 시작하고 오염이 실측되면 승격 |
| 법적 지위 | **제품 이름 명사만 수집·노출**(브랜드 별도 입력란도 안 만든다 — 폼 무거워짐) — 효능·기능성은 사용자 입력에서 받지도, 크라우드 제안에 보여주지도 않는다. 뱃지·SPF/PA는 **mfds 스냅샷 전용으로 유지**(v2-2 §3-4 방패 불오염). 제품명 표시는 지시적 사용(nominative use)이라 상표 리스크 낮음 | 사용자에게 카테고리·브랜드 입력을 더 받기 — 폼이 무거워지고 오정보 축만 는다 |

**출처 구분(서버 응답 → 화면)**: 크라우드 제안은 응답에 `source: 'community'`로 표기되고,
클라는 ① 제안 줄에 구분 표시(예: 「사용자 등록」 캡션) ② 선택 시 `mfds`가 아니라
`crowd` 필드로 저장(§4-3) ③ 카드에 뱃지·SPF 없음 — 기존 출처 캡션(「기능성 표시는 식약처
… 기준이에요」)이 계속 참이다. 검색 병합은 MFDS 직호출과 서버 검색을 병렬로 부르고 MFDS
결과 먼저·크라우드 뒤 붙이기(정규화 키로 중복 제거, 합계 10건 컷) — 어느 쪽이 죽어도
남은 쪽만 뜬다(무음).

### 3-6. 호스팅 — 기존 BookTimer 인스턴스에 동거 + MySQL 재사용 ✅ (사용자 결정 2026-09-01)

**전제 정정 2회**: 초안은 Render+Neon이었고, 사용자 결정(2026-08-30)으로 AWS 신규 인스턴스가
됐다. 그리고 **2026-09-01 AWS 실측(§2-5)이 그 전제를 다시 뒤집었다** — 프리티어는 없고(크레딧
0원 적용·8월 $32.80 실결제), 서울에 **t3.small이 이미 돌고 있다**. 새 인스턴스는 첫 달부터
월 ~$15.9인데, 기존 박스에 얹으면 **0원**이다.

| 대안 | 추가 월 비용 | 격리 | 만들어야 하는 것 | 판정 |
|---|---|---|---|---|
| **A. 기존 t3.small에 동거 + MySQL 재사용** | **0원** | 컨테이너 `mem_limit`이 경계 | Caddy 블록 3줄 · MySQL DB 1개 · A 레코드 1개 · 컨테이너 1개 | ✅ **채택(사용자 결정)** |
| B. 신규 t3.micro | ~$15.9 | 완전 | 인스턴스·EIP·보안그룹·IAM 역할·certbot·Postgres — 구판 §5 전체 | 기각 — 부하가 수십 KB 왕복인데 격리에 월 2.2만원은 이르다. **분리 경로(§3-6-1)로 남긴다** |
| C. t3.small → t3.medium 승격 후 동거 | ~$19 | 여전히 동거 | 재시작 1회 | 기각 — B보다 비싼데 격리는 못 얻는다 |
| D. Render 무료 웹 + Neon 무료 Postgres | 0원 | 완전 | 최소 | **되돌아갈 길로 유지**(§2-4) — 다만 A가 이미 0원이라 회귀 동기가 사라졌다 |

**결정의 근거는 비대칭이다**(§2-5 ④): CPU 평균 1.8~2.2% · 크레딧 576/576 만점 고정 ·
디스크 24GB 여유. **CPU와 디스크는 남아돌고, 빠듯한 것은 메모리뿐**이다. Spring 하나 더
얹는 일은 CPU 관점에서 아무 일도 아니다.

**동거로 통째로 사라진 것들(구판 설계에서 삭제)**:

| 구판에 있던 것 | 왜 사라졌나 |
|---|---|
| Elastic IP 확보와 그 인과 | 기존 EIP `15.165.95.129`를 A 레코드가 가리킨다 |
| nginx + certbot + `certbot.timer` + 갱신 실패 이중 감시 | **리버스 프록시가 Caddy**다 — ACME 발급·갱신이 내장이라 만들 것도 감시할 것도 없다. 구판이 「최대 함정」이라 부른 항목이 통째로 소멸 |
| Postgres 설치·파라미터 튜닝·`listen_addresses` 이중 차단 | **MySQL 8.4 컨테이너 재사용**(데이터베이스 1개 추가) — 컨테이너를 안 띄우니 메모리 +0MB. 3306은 애초에 호스트에 노출돼 있지 않다(컨테이너 네트워크 내부) |
| 보안그룹 신설·인스턴스 IAM 역할·SSM 셋업 | 이미 있다(SSM 에이전트 Online 실측) |
| swap 2GB 파일 생성 | 이미 2GB 잡혀 있다 |
| `setup.sh` 멱등 부트스트랩 | 부트스트랩할 호스트가 없다 — compose 조각 하나로 대체 |
| CloudFront·ALB 기각 논의 | 도메인+Caddy로 무의미해졌다 |

**메모리 예산(동거의 유일한 대가 — 수치로 박는다)**:

| 항목 | `mem_limit` | 실사용(2026-09-01) |
|---|---|---|
| `booktimer-app-blue`/`-green`(**둘 중 하나만 상시**) | 700MB | 428.6MB |
| `booktimer-mysql-1` | 600MB | 240.1MB |
| `booktimer-caddy-1` | 128MB | 27.1MB |
| **`facefit-api`(신설)** | **320MB** | 목표 250~300MB |
| OS·기타 | — | ~150MB |

- **평시**: 428.6 + 240.1 + 27.1 + ~300 + ~150 ≈ **1.15GB / 1.91GB — 여유 ~760MB.** 넉넉하다.
- ⚠️ **배포 순간이 진짜 제약이다(늦게 발견 — 정직하게 적는다).** BookTimer는 blue/green
  배포라 **전환 중 app 컨테이너가 2개** 뜬다. BookTimer 자신의 예산 주석이 그 순간을
  **1.78GB**로 잡아 두었고 「초과분은 swap 2GB가 흡수한다」고 명시한다. 여기에 facefit
  ~300MB가 얹히면 **약 2.08GB > 1.91GB**라, **BookTimer가 배포할 때마다 ~200MB가 swap으로
  밀린다**. 실측된 swap 653MB 사용도 이 창의 흔적일 가능성이 높다.
- **그래서 facefit의 몫을 320MB로 깎았다**(초안 400MB에서 하향). 이 창을 못 없애니 **작게
  만드는 것이 유일한 통제**다.
- **감내 가능한 이유**: 그 창은 배포당 수십 초이고, 양쪽 다 지연에 관대하다 — facefit은
  fire-and-forget 백업이라 그 사이 PUT이 실패해도 클라가 `backupDirty`를 세우고 **다음 앱
  시작 때 재시도**한다(§3-3). 즉 **swap 지연이 사용자에게 도달하지 않고 구조적으로 흡수된다.**
- 상한 합계(1,748MB)는 물리 메모리에 근접하지만 **상한의 목적은 총량 예약이 아니라 격리다** —
  facefit이 새면 facefit만 죽고 BookTimer는 산다. 상한이 없으면 호스트 OOM 킬러가 둘 중
  아무나 고른다.
- JVM: **`-Xmx160m -XX:MaxMetaspaceSize=96m -XX:+UseSerialGC`**. 작은 힙에서는 SerialGC가
  G1보다 메모리를 덜 쓴다. 이 워크로드(수십 KB 블롭 왕복)에 160MB 힙은 남아돈다.
  ⚠️ BookTimer는 `-XX:MaxRAMPercentage=50`으로 상대 지정을 쓰는데, facefit은 **절대값으로
  박는다** — 상한을 낮췄을 때 힙이 같이 줄어드는 편이 안전하고, 수치가 문서와 일치한다.
- Hikari `maximumPoolSize=5`(기본 10 하향) — 커넥션 하나가 곧 MySQL 쪽 메모리다.
  MySQL은 이미 `--innodb-buffer-pool-size=256M`으로 고정돼 있어 DB 1개 추가에 재조정이 없다.
- ⚠️ **RSS 250~300MB는 추정이지 실측이 아니다.** v3-1 태스크 3의 완료 조건에 `docker stats`
  실측 1회 + **BookTimer 배포 1회를 겹쳐 돌린 뒤의 `free -m`**을 박는다(§6).

**HTTPS — 함정이 아니라 세 줄이다.** `facefit-api.booktimer.app` A 레코드 →
`15.165.95.129`(Route 53 영역 `Z0795663J1W7C48SU27B`). Caddy 사이트 블록이 인증서 발급·갱신을
자동으로 한다.

- **A 레코드가 먼저 서야 한다** — Caddy의 ACME HTTP-01 검증이 도메인 해석에 의존하므로,
  레코드 없이 블록을 올리면 발급 재시도만 돈다.
- ⚠️ **TTL은 60초로 만든다.** 기본값(300~3600초)으로 두면 나중에 분리할 때 전환이 그만큼
  늦다. **지금 60초로 박는 것이 미래의 분리 비용을 미리 깎는 유일한 준비다**(§3-6-1 ④).

**DB 격리 — 인스턴스는 공유해도 자격증명은 나눈다.** `facefit` 데이터베이스 + 전용 `facefit`
MySQL 사용자를 만들고 **그 DB에만** 권한을 준다. facefit 자격증명이 새도 BookTimer 데이터에
닿지 못해야 하고, 분리할 때 덤프·이관 경계가 자동으로 그어진다. 문자셋 `utf8mb4`(한글).

#### 3-6-1. 분리 경로 — 비대해졌을 때 길을 잃지 않도록 (사용자 요구 2026-09-01)

동거는 **되돌릴 수 있을 때만** 옳은 결정이다. 그 되돌리는 길을 지금 적어 둔다.

**① 무엇이 묶여 있나 — 분리 시 풀어야 할 전부**

| # | 결합 | 분리 시 할 일 |
|---|---|---|
| 1 | Caddy vhost | facefit 스니펫을 새 박스의 프록시로 옮김 |
| 2 | MySQL 인스턴스 공유(`facefit` DB·사용자) | `mysqldump facefit` → 새 MySQL 복원 |
| 3 | Docker 네트워크 공유 | 새 박스의 compose가 자기 네트워크를 가짐 |
| 4 | 호스트 메모리 공유 | 소멸(그것이 분리의 목적) |
| 5 | 배포 경로(같은 ECR 레지스트리·같은 SSM 대상 인스턴스) | 워크플로의 대상 인스턴스 ID 교체 |
| 6 | A 레코드가 BookTimer의 EIP를 가리킴 | 새 EIP로 변경(TTL 60초라 1분) |
| 7 | DB 덤프 cron이 같은 호스트에서 돎 | cron 이설 + 옛 것 제거 |

**② 언제 분리하나 — 감이 아니라 신호로**

- 호스트 `available` 메모리가 **지속적으로 300MB 아래**로 내려간다.
- facefit 컨테이너가 **OOM으로 재시작된 이력**이 생긴다(`docker inspect`의 `OOMKilled: true`).
- MySQL 슬로우 쿼리가 두 서비스 부하로 실측된다.
- BookTimer의 배포·재시작이 facefit 때문에 지연되거나 서로를 흔든다.
- facefit 트래픽이 BookTimer와 같은 자릿수가 된다.

하나 걸리면 **판단**하고, 둘 이상이면 **분리한다**.

**③ 어떻게 분리하나 — 반나절 · 무중단은 아니지만 안전하다**

1. 새 인스턴스(t3.micro 이상) + EIP 생성.
2. 새 박스에 compose 기동 — Caddy(또는 nginx) + facefit + MySQL.
3. `mysqldump facefit` → 새 MySQL 복원 → 데이터 대조.
4. **A 레코드를 새 EIP로 변경**(TTL 60초 → 1분 내 전환).
5. 확인 후 옛 박스에서 facefit 컨테이너·Caddy 스니펫·`facefit` DB·사용자·cron 제거.

전환 중 잠깐 끊겨도 **앱은 v2와 동일하게 돈다** — 모든 서버 경로가 무음 폴백이라 백업·크라우드
제안만 조용히 쉰다. **이것이 분리를 위험하지 않게 만드는 구조적 이유다.**

**④ 지금 해 두면 그때 싸지는 것 — 넷 다 이번 계단에 포함한다**

- **A 레코드 TTL 60초** — ③의 4단계가 1분이 된다.
- **전용 MySQL 사용자·DB** — ③의 3단계 경계가 자동으로 그어진다.
- **compose·Caddy 조각을 facefit 레포에 둔다**(§3-7) — ③의 2단계가 파일 복사가 된다.
- **DB 접속 정보를 환경변수로 주입**(하드코딩 금지) — 호스트가 바뀌어도 이미지는 그대로다.

이 넷을 지키면 분리는 「새 박스 세우고 · 파일 옮기고 · 레코드 바꾸기」로 줄어든다.
안 지키면 그때 설계를 다시 해야 한다.

**⑤ BookTimer 쪽에도 흔적을 남긴다**(사용자 지시 2026-09-01). BookTimer 세션이 AWS 장애를
디버깅할 때 **정체 모를 `facefit-api` 컨테이너가 자원을 먹고 있으면 길을 헤맨다.** BookTimer
레포에 동거 사실·자원 몫·「facefit만 끄는 법」·이 문서 링크를 남기는 것을 v3-1 태스크에 포함한다(§6).

| Caddy 사이트 블록 | **BookTimer 레포**(`deploy/caddy/Caddyfile`) — 1회 추가 | 그 디렉터리가 프록시 설정의 단일 출처이고 배포 스크립트가 거기서 동기화한다. 별도 파일 + `import`도 가능하지만 **어차피 같은 레포**라 간접만 는다 — 그리고 **한 파일에 다 보이는 편이 디버깅하는 사람에게 친절하다** |
| 동거 사실·자원 몫·끄는 법 | **BookTimer 레포 문서 + `CLAUDE.md` 포인터** | §3-6 ⑤ — 미래의 BookTimer 세션이 정체 모를 컨테이너에 헤매지 않게 |

⚠️ Caddy가 `facefit-api:8080`을 이름으로 찾으려면 **두 컨테이너가 같은 도커 네트워크**에 있어야
한다(BookTimer 프로젝트의 기본 네트워크에 facefit이 `external`로 참여). 네트워크 실명은
배포 시 `docker network ls`로 확인한다 — 태스크 3의 선행 항목.

### 3-8. 문구·검수 갱신 ✅

v2-2 §3-5의 「낡는 문장을 능동적으로 고친다」 관례 계승:

- **불변**: `LOCAL_ONLY`(사진 문장) — 글자 하나 안 바뀐다. 이것이 이 설계의 성과다.
- **갱신**: ① 콘솔 상세 설명 — 「제품 검색 시에만 식약처 공공 데이터 조회」 뒤에
  「백업을 켜면 제품·관찰 기록이 서버에 저장돼요(사진 제외). 직접 등록한 제품 이름은
  익명으로 모아 다른 사용자 검색에 쓰일 수 있어요」 ② 온보딩 프라이버시 항목 같은 취지
  한 줄 ③ 릴리스 노트 선제 고지 — 「기록 백업(옵트인·사진 미포함)과 제품 이름 익명 공유가
  추가됐어요. 서버에는 개인 식별 정보가 저장되지 않아요」(검수자가 발견하기 전에 먼저 말한다).
- 개인정보처리방침 별도 등록 경로는 콘솔에 없다(v1 태스크 10 실측) — 상세 설명 + 온보딩
  내장 방식 유지. 단 **백업은 「수집」의 시작이라 반려 리스크가 v2-2보다 높다** — 반려 사유가
  다음 문구의 입력이다(§8).

### 4-2. API · 스키마

**공통**: 인증 헤더 `X-Anon-Key: <hash>`(백업 계열 필수 · 크라우드 등록 필수 · 검색은 불요).
서버는 수신 즉시 sha256으로 바꿔 쓰고 **원 키를 저장·로깅하지 않는다**. 키 형식은 불투명
문자열로 취급(길이 8~128 검증만 — 구조 가정 금지, §8). 레이트리밋: IP당 60회/분 전역 ·
백업 PUT 키당 6회/분 · 검색 IP당 30회/분 — 인메모리 고정 창
(`// ponytail: 단일 인스턴스 전제 — 수평 확장하는 날 Redis로`). 초과는 429.

```
GET  /health                    → 200 (모니터링·배포 검증용 — 바디 없음)

PUT  /v1/backup                 X-Anon-Key 필수
     body { schemaVersion: 1, products: [...], notes: {...}, clientSavedAt: 'ISO' }
     → 200 { savedAt }
     검증: ① 본문 ≤ 512KB ② 최상위 키 화이트리스트(위 4개 외 → 400)
          ③ **재귀 문자열 길이 ≤ 2,000자**(§3-2 불변식의 서버측 집행 — 사진 base64 차단)
          ④ products ≤ 200건 · notes ≤ 4,000키
     ⚠️ products 항목 내부는 불투명(opaque)하게 저장한다 — 클라의 미지 필드 보존 규칙
        (v1 §4-2)과 짝. 서버가 제품 필드를 화이트리스트하면 v4 클라 필드가 백업에서 증발한다.

GET  /v1/backup                 X-Anon-Key 필수 → 200 블롭 그대로 | 404
DELETE /v1/backup               X-Anon-Key 필수 → 204 (백업 끄기 — 즉시 삭제)

POST /v1/products               X-Anon-Key 필수
     body { name }  (≤ 100자 · 공백 제거 후 2자 미만 400)
     → 204. 서버가 normKey = 소문자화+공백제거로 병합, (normKey, keyHash) 유니크로
       같은 사람 중복 등록은 1인으로 계수.

GET  /v1/products/search?q=     → 200 { items: [{ name, source: 'community' }] }
     노출 조건: 등록 2인 이상 AND NOT hidden. 대조는 v2-3 술어와 같은 규칙 —
     쿼리 토큰 전부가 normKey에 부분문자열(AND). 최대 10건.
     `// ponytail: LIKE 전수 스캔 — 수천 행까지 문제없고, 느려지면 ngram FULLTEXT 인덱스`

POST /v1/products/report        body { name } → 204 (normKey로 reports 증가 —
     hidden 전환은 운영자 SQL 수동. 자동 임계는 오탐 실측 전 YAGNI)
```

```sql
-- Flyway V1 — MySQL 8.4(기존 booktimer-mysql-1 컨테이너의 `facefit` 데이터베이스)
CREATE TABLE backup (
  key_hash        CHAR(64)     NOT NULL PRIMARY KEY,  -- sha256(anon key) hex — 원 키 비저장(§3-1)
  payload         MEDIUMTEXT   NOT NULL,              -- 불투명 저장(아래 ⚠️)
  client_saved_at VARCHAR(32)  NULL,
  updated_at      DATETIME(3)  NOT NULL               -- UTC(§4-1)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE community_product (
  norm_key      VARCHAR(255) NOT NULL PRIMARY KEY,    -- 소문자화+공백제거(클라 norm과 동일 술어)
  display_name  VARCHAR(255) NOT NULL,                -- 최초 등록 원문(§3-5)
  registrations INT          NOT NULL DEFAULT 1,
  reports       INT          NOT NULL DEFAULT 0,
  hidden        BOOLEAN      NOT NULL DEFAULT FALSE,
  created_at    DATETIME(3)  NOT NULL,
  updated_at    DATETIME(3)  NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE community_registration (    -- 「서로 다른 2인」의 근거
  norm_key VARCHAR(255) NOT NULL,
  key_hash CHAR(64)     NOT NULL,
  PRIMARY KEY (norm_key, key_hash)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**MySQL이라서 달라진 것(Postgres 초안과의 차이 — 옮길 때 밟는 지뢰들)**:

- ⚠️ **`payload`는 `JSON`이 아니라 `MEDIUMTEXT`다.** 두 가지 이유가 겹친다. ① MySQL의 `JSON`
  타입은 저장 시 **정규화**한다(공백 제거·객체 키 재정렬) — §4-2가 요구하는 「클라의 미지
  필드를 있는 그대로 왕복 보존」이 **바이트 단위로는 깨진다**. ② `TEXT`는 64KB라 512KB 상한을
  못 담는다 — `MEDIUMTEXT`(16MB)가 최소 크기다. 서버가 블롭 내부를 질의하지 않으므로 JSON
  타입의 이점이 애초에 없다.
- **`TEXT`는 PK가 될 수 없다**(접두 길이 없이는). sha256 hex는 항상 64자라 `CHAR(64)`가 정확하고,
  `norm_key`는 `VARCHAR(255)`로 고정한다 — 복합 PK 크기 `255×4 + 64 = 1,084바이트`로
  InnoDB 인덱스 한도(3,072)에 여유가 있다.
- **`TIMESTAMPTZ` → `DATETIME(3)` + UTC 규약**(§4-1). MySQL `TIMESTAMP`는 세션 타임존으로
  자동 변환해 조용히 밀릴 수 있어 쓰지 않는다.
- `JSONB` 인덱싱·`pg_trgm` 같은 Postgres 고유 기능은 애초에 안 쓰던 것이라 잃은 게 없다.

  dirty면 재업로드 ④ 온보딩 하단 「기기를 바꿨나요? 기록 복원」 → 미리보기(사진 미복원

## 5. 운영 (BookTimer EC2 동거 · 서울 ap-northeast-2)

> **구판 대비 대부분이 삭제됐다.** 인스턴스·Elastic IP·보안그룹·IAM 역할·swap·nginx·
> certbot·Postgres·`setup.sh`가 전부 **이미 있거나 불필요**해졌다(§3-6). 아래에 남은 것은
> **facefit이 실제로 더하는 것**뿐이다.

- **호스트**: `i-07a649585c25707a3`(t3.small · 서울 · EIP `15.165.95.129` · SSM Online).
  ⚠️ **AWS CLI는 반드시 `--profile booktimer`** — `default`는 **다른 계정**의 CI 사용자라
  Route 53·S3·IAM·SSM이 전부 권한 거부다(§2-5 ③). 이걸 모르면 「권한이 없다」를
  「리소스가 없다」로 오독한다.
- **HTTPS**: Caddy가 발급·갱신을 전담한다 — **구판의 certbot·타이머·이중 감시가 통째로
  삭제**됐고 facefit이 더하는 운영 항목은 **0**이다. BookTimer Caddyfile에 블록 하나:
  ```
  facefit-api.booktimer.app {
      reverse_proxy facefit-api:8080
      encode gzip zstd
  }
  ```
  ⚠️ 그 Caddyfile은 **디렉터리 마운트**로 실려 있고(파일 마운트는 inode 고정 탓에 변경이
  조용히 무반영 — BookTimer T-167) 배포 스크립트가 `aws s3 sync`로 나른다. 즉 **facefit
  블록은 BookTimer의 배포 경로를 한 번 타야 반영된다.**
- **보안 — facefit이 새로 여는 포트는 0개**: 컨테이너 8080은 **호스트에 노출하지 않고**
  도커 네트워크 안에서만 Caddy에게 말한다. MySQL 3306도 마찬가지다(실측 — 호스트 리스너
  목록에 없다). 보안그룹은 80/443 그대로 **변경 없음**.
- **DB 계정 분리**(§3-6):
  ```sql
  CREATE DATABASE facefit CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
  CREATE USER 'facefit'@'%' IDENTIFIED BY '<SSM에서>';
  GRANT ALL PRIVILEGES ON facefit.* TO 'facefit'@'%';
  ```
  BookTimer 데이터에 닿는 권한을 **주지 않는 것**이 요점이다 — 자격증명이 새도 경계가 남고,
  분리할 때 덤프 범위가 자동으로 그어진다.
- **시크릿**: **SSM Parameter Store**(BookTimer와 같은 습관) — `/facefit/db-password` 등
  SecureString. 컨테이너에는 환경변수로 주입한다(하드코딩 금지 — §3-6-1 ④).
  ⚠️ **로컬 Git Bash에서 SSM을 부를 땐 `MSYS_NO_PATHCONV=1`** — `/facefit/...` 이름이 Windows
  경로로 무성 변환돼 **존재하는 파라미터를 「없다」로 오판**한다(글로벌 Windows 셸 원칙 5번).
- **배포**: GitHub Actions(main 머지 · `paths: server/**`) — ① `server/` 테스트 ② 도커
  이미지 빌드 → **ECR**(BookTimer와 같은 레지스트리의 별도 리포지토리 `facefit`)
  ③ `aws ssm send-command`로 `docker compose -f compose.facefit.yaml up -d`.
  **blue/green은 안 만든다** — 재시작 수 초의 공백은 무음 폴백이 흡수하는데(§3-3),
  blue/green은 배포 순간 메모리를 2배로 쓰고 **그게 이 박스의 가장 아픈 자리**다(§3-6).
  `// ponytail: 단순 재시작 — 다운타임이 실사용 불만으로 실측되면 그때 blue/green`
  Actions 자격은 **GitHub OIDC 역할** 권고(장기 키 무저장). PR CI는 `server/`+`miniapp/`
  테스트(워크플로 신설 — 현재 레포에 없음, 실측). 클라는 기존 `npm run release` 그대로 —
  서버 URL은 `VITE_API_BASE`(.env, MFDS 키 옆).
- **DB 백업 — 새로 만들기 전에 있는 것을 본다**: BookTimer에 **이미 `deploy/backup-mysql.sh`가
  있다**(`deploy/tests/test-backup-mysql.sh`까지 있는 실물). 1순위는 **그 스크립트가 `facefit`
  데이터베이스도 덤프하도록 대상에 추가**하는 것이다 — **백업 경로가 둘이면 하나가 조용히

  문서 링크를 남기고 **`CLAUDE.md`에 포인터 한 줄**을 넣는다(매 세션 로드되는 파일이라

## 8. 리스크 · 미검증 가정

1. **[최대] 익명 키의 기기 간 동일성** — 이 설계의 복원 축이 통째로 얹힌 가정. v3-2가
   검증 계단이고, 실패 시 폴백 사다리(§3-1)가 준비돼 있다. **v3-1 출시 시점엔 복원을
   과약속하지 않는다** — 문구는 「기기를 바꿔도 복원될 수 있어요」가 아니라 백업 사실만
   말하고, 복원 확답 문구는 v3-2 통과 후에 쓴다.
2. **기기 이전 시 사진은 사라진다** — 의도된 한계(§3-2 사용자 결정). 복원 미리보기의 사전
   고지가 유일한 완충이고, 보완책(앨범 내보내기)은 별도 계단. 타임랩스 재료가 못 넘어가는
   앱의 구조적 아픔으로 문서에 남긴다.
3. **토스에 익명 키 서버 검증 API가 있는지 미확인** — 없다는 전제로 capability 모델을
   설계했다. 있다면 어뷰즈 방어가 한 계단 싸진다(발견 시 보너스 방향 — 설계 변경 불필요).
4. **익명 키의 엔트로피** — 「HASH 타입」이라는 형식만 실측됐다. 추측 가능한 구조라면
   소유 증명이 약해진다 — v3-2 실측 시 키 길이·형식을 함께 기록하고, 짧으면 레이트리밋
   강화(GET 백업 IP당 회수 하향)로 대응.
5. **검수 리스크(수집의 시작)** — 수집 0으로 4연속 무반려였던 앱이 처음 「서버 저장」을
   말한다. 선제 고지(§3-8)로 흡수하되 반려 확률은 v2-2 때보다 높다 — 반려 사유가 문구
   개정의 입력이다(관례).
6. **[동거] BookTimer와 장애 반경을 공유한다** — 비용 리스크는 **해소**됐다(추가 0원.
   §2-5로 프리티어 부재가 확정되면서, 오히려 신규 인스턴스가 월 ~$15.9짜리 위험한 선택이
   됐다). 그 대가로 **한 박스가 죽으면 둘 다 죽는다.** 방향은 비대칭이다: ① facefit이
   메모리를 새면 `mem_limit: 320m`이 **facefit만** 죽인다(설계된 방어) ② **BookTimer 쪽
   사고·재부팅·배포 실수는 facefit이 통째로 맞는다 — 이쪽엔 방어가 없고, 수용한다.**
   하한선은 mysqldump S3(§5)이고 다운 중에도 전 경로 무음 폴백이라 **앱은 v2로 동작**한다.
   분리 신호와 절차는 §3-6-1.
7. **크라우드소싱 콜드 스타트** — 2인 기준이라 사용자가 적은 동안 노출이 0에 수렴한다.
   의도된 트레이드오프(품질 우선)이고, 등록 데이터는 기준 미달이어도 쌓인다 — 사용자가
   늘면 소급 노출된다. 영영 0이면 기준을 1+report로 낮추는 판단을 그때 한다.
8. **`saveBase64Data` 반복 호출의 실기기 거동**(보완책 계단의 선행 실측) — 앨범 권한
   프롬프트 빈도·호출 rate 제한·대량 저장 시간이 전부 미실측. 그 계단의 태스크 1이다.
9. **[메모리] BookTimer 배포 창이 진짜 제약이다** — 구판의 최대 리스크였던 「certbot 갱신
   실패 = 전면 불통」은 **Caddy 채택으로 소멸**했다(발급·갱신이 내장). 대신 남은 상시
   리스크는 메모리 하나다: BookTimer가 blue/green 배포로 app 컨테이너 2개를 띄우는 수십 초
   동안 **합계가 물리 메모리를 ~200MB 초과**해 swap으로 밀린다(§3-6 산수 — 실측 swap
   653MB 사용이 그 흔적으로 보인다). 방어는 셋: ① facefit 몫을 320MB로 깎아 둔 것
   ② swap 2GB ③ 무음 폴백이 지연을 사용자에게 도달하기 전에 흡수하는 구조.
   **아직 미실측이라 태스크 3-h에서 배포를 겹쳐 돌려 `free -m`으로 확인**하고, 예산을
   넘으면 그 자리에서 상한을 조정한다. 반복되면 §3-6-1의 분리 신호로 넘어간다.
10. **[동거] BookTimer 세션이 facefit을 모른다** — AWS 장애를 디버깅하는 미래의 BookTimer
   세션이 정체 모를 `facefit-api` 컨테이너에 시간을 쓸 수 있다(사용자가 짚은 리스크,
   2026-09-01). 방어는 문서 하나뿐이라 **`CLAUDE.md` 포인터가 실제로 들어갔는지**가
   태스크 3-e의 완료 조건이다 — 문서가 있어도 로드되는 파일에서 링크되지 않으면 없는 것과 같다.
