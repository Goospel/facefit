# 비기능성 화장품 제품 커버리지 리서치 (2026-08-30)

> 선행: [2026-08-29 화장품 데이터 API 리서치](2026-08-29-cosmetics-data-api-research.md) — 그 결론(전 제품
> 공적 등록부 없음 · 코리안넷 건당 유료 · 공공 바코드 API 2018 동결 · OBF 얇음 · 화해 API 없음) 위에 쌓는다.
> 이번 질문: ① 비기능성(일반) 화장품 제품 단위 조회는 유료(코리안넷)뿐인가 ② 기존 앱들은 DB를 어떻게 만들었나.

## 결론 3줄

1. **"무료 + 서버 0 + 전 제품 커버리지"를 동시에 주는 경로는 없음이 재확인됐고, 상황은 더 나빠졌다** —
   유일한 실질 후보였던 네이버 쇼핑 검색 API가 **2026-07-31 24:00부로 완전 종료**(기존 이용자 포함, 공식 대체
   없음 — 약관 부칙 원문 실측). 카카오 검색 API에는 쇼핑 카테고리 자체가 없다.
2. **Open Beauty Facts 실측: 15개 쿼리 중 5건 히트, 한글 쿼리 0/5건** — 해외 수출 인기 K뷰티(조선미녀·스킨1004)만
   있고 내수 색조·클렌징·한글 검색은 전멸. 보조 소스로도 못 쓴다.
3. **기존 앱들(화해·글로우픽·언니의파우치)의 DB는 API가 아니라 운영 프로세스다** — 브랜드가 엑셀 양식을
   이메일로 제출하고 운영팀이 수작업 등록 + 사용자 제보. 서버 0 개인 프로젝트가 흉내낼 모델이 아니므로,
   facefit의 다음 계단은 **"DB에 없는 제품은 사용자가 직접 입력(로컬 커스텀 제품)"**이 정답이다.

## 질문 1 — 경로별 평가

판정 기준: 무료 / 서버 0 유지(클라 직호출) / 커버리지 / 약관·법적 리스크 / facefit 실요구(제품명 자동완성 + 카드 메타) 충족.

| 경로 | 무료 | 서버 0 | 커버리지 | 리스크 | 판정 |
|---|---|---|---|---|---|
| 네이버 쇼핑 검색 API | - | ✕ (CORS 없음 실측) | - | - | **사망 — 2026-07-31 서비스 종료** |
| 카카오 (Daum) 검색 API | ○ | ○ (CORS `*` 실측) | **✕ 쇼핑 검색 없음** | - | 불가 — 제공 카테고리에 상품이 없다 |
| 쿠팡 파트너스 API | △ | ✕ | ○ | 높음 | 불가 — 판매실적 15만원 승인장벽 + Search 시간당 10회 |
| Open Beauty Facts | ○ | ○ | **✕ 실측 5/15, 한글 0/5** | 낮음 | 불가 — 내수 제품·한글 검색 전멸 |
| 식약처 추가 데이터셋 | ○ | △ | ✕ 업체 단위 | 낮음 | 불가 — 제품(품목) 단위가 아님 |
| 올리브영·다이소 유통사 API | - | - | - | - | 부재 — 공개 오픈 API 없음(미확인 한계 있음) |
| 코리안넷(선행 조사) | ✕ 건당 유료 | ✕ | ○ | 낮음 | 후순위 유지(선행 결론 그대로) |

**답: 사실상 그렇다.** "전 제품을 제품 단위로 조회"하는 경로는 코리안넷(유료)뿐이고, 이번 조사로 무료 우회로
후보가 전부 실측 탈락했다. 단 질문을 facefit의 실요구로 좁히면 답이 달라진다 — 아래 「다음 계단 후보」.

### ① 네이버 쇼핑 검색 API — 조사 중 사망 확인 (실측)

- 문서 스펙(참고용): 일 25,000회 무료, `X-Naver-Client-Id/Secret` 헤더 인증, 응답 필드
  title·image·lprice·mallName·productId·brand·maker·category1~4 — 자동완성+카드 메타에 이상적이었다.
  (출처: [developers.naver.com 쇼핑 검색 문서](https://developers.naver.com/docs/serviceapi/search/shopping/shopping.md) — curl 실측)
- **CORS 실측**: `openapi.naver.com`에 OPTIONS 프리플라이트 → `Access-Control-Allow-*` 헤더 없음(400).
  브라우저 직호출 불가 = 살아 있었어도 서버(프록시) 필수 + 클라 키 노출 문제.
- **약관 실측** ([NAVER API 이용약관](https://developers.naver.com/products/terms/), curl로 원문 확보):
  - 일반조건 7조 금지행위 ③: 「본 약관에서 허용한 범위를 넘어서서 무단으로 **복제, 저장(캐시 행위 포함),
    가공, 배포** 등 이용하거나 제3자에게 제공하는 행위」 · 예시 「~수집하여 **별도 데이터베이스로 관리하며
    이용하는 행위**」 — 검색 결과를 앱 DB로 축적하는 이용은 살아 있었어도 약관 위반.
  - 검색 API 특약 2.1: 「검색결과를 독립적으로 노출하여야 하며 ~ 임의로 수정 및 변조해서는 안 됩니다」.
  - **부칙(2026-07-31 시행) 제2조 ③: 「'Search API' 중 '쇼핑', '책', '학술정보' 데이터 제공 서비스는
    2026년 7월 31일 24:00부로 종료됩니다. 해당 서비스 종료 시점 기준 기존 이용자라 하더라도 2026년 8월 1일
    00:00부터는 해당 API를 더 이상 이용할 수 없습니다.」** — NCP NAVER API HUB 이관 대상에서도 쇼핑은 빠졌고,
    공식 대체 API 없음(2차 확인: [와플보드 이관 가이드](https://waffleboard.io/blog/naver-search-api-hub-migration-guide)).

### ② 카카오 (Daum) 검색 API — CORS는 열려 있으나 쇼핑이 없다 (실측)

- CORS 실측: `dapi.kakao.com` OPTIONS → `Access-Control-Allow-Origin: *` (204). 클라 직호출을 공식 지원하는
  구조 — **서버 0 조건을 만족하는 유일한 상업 API**였다.
- 그러나 제공 카테고리는 웹문서·동영상·이미지·블로그·책·카페 6종뿐 — **상품/쇼핑 검색이 없다**
  ([카카오디벨로퍼스 Daum 검색 문서](https://developers.kakao.com/docs/latest/ko/daum-search/common)).
  블로그/웹문서 검색으로 제품명을 간접 추출하는 우회는 정형 메타(브랜드·이미지·카테고리)가 없어 실요구 미달.

### ③ Open Beauty Facts — 커버리지 실측 (2026-08-30, search.pl API)

한국 인기 제품 15개 쿼리 실측 (`world.openbeautyfacts.org/cgi/search.pl`):

| 쿼리 | 히트 |
|---|---|
| round lab dokdo toner | **1** (8809657114731) |
| anua heartleaf toner | **1** (8809640736025) |
| beauty of joseon | **14** (브랜드) |
| skin1004 centella | **10** (브랜드) |
| innisfree green tea | **1** |
| banila co clean it zero | **1** |
| torriden dive-in serum / cosrx snail mucin / isntree hyaluronic toner / etude soon jung | 0 |
| **한글 5종** (라운드랩 독도 토너 · 쿤달 클렌징폼 · 센카 퍼펙트 휩 · 클리오 킬커버 · 롬앤 쥬시 래스팅 틴트) | **전부 0** |

- 히트는 전부 **해외 수출로 유명한 K뷰티 + 영문 쿼리**. 내수 클렌징·색조는 0, **한글 제품명 검색은 0/5**.
- facefit 사용자는 한글로 입력한다 → 자동완성 소스로 성립 불가. 선행 조사의 「얇음」이 「사실상 없음」으로 확정.

### ④ 그 외 경로

- **식약처 추가 데이터셋**: [화장품 관련 정보(15020628)](https://www.data.go.kr/data/15020628/openapi.do)는
  화장품 제조업·책임판매업 **업체 정보 조회**(업체명·대표자·허가일자) — 제품 단위 아님.
  [화장품 규제정보(15111773)](https://www.data.go.kr/data/15111773/openapi.do)는 규제 성분 정보.
  의약외품 품목허가 데이터는 치약·염모제 등 의약외품 영역 — 일반 화장품과 무관.
  식의약 데이터 포털(data.mfds.go.kr)에도 일반 화장품 품목 단위 데이터셋은 없다(선행 결론과 일치 —
  보고·허가 대상이 아니라서 데이터 자체가 국가에 없다).
- **올리브영·다이소**: 공개 개발자 포털·오픈 API 없음. CJ올리브네트웍스 'API PLEX'는 B2B API 마켓이지
  상품 카탈로그 공개가 아니다. *(한계: 부재 증명은 검색 기반 — 비공개 제휴 API 존재 가능성은 배제 못 함)*
- **쿠팡 파트너스 API**: 상품 검색은 있으나 제휴수익 실적(판매 15만원) 후 최종승인 + **Search API 시간당
  10회·10개 제한** — 자동완성 용도로 구조적으로 부적합. 약관도 제휴 링크 노출 목적으로 한정.

## 질문 2 — 기존 앱들의 제품 DB 구축 방식

| 서비스 | 구축 방식 | 근거 수준 |
|---|---|---|
| 화해(버드뷰) | 초기: 창업자 수작업 성분 정리 → 현재: 브랜드 셀프 서브미션(엑셀+서류 이메일) + 운영팀 | 공개 근거 실측 |
| 글로우픽 | 브랜드 셀프 서브미션(가이드 PDF + 엑셀 템플릿 + 누끼컷 → db@glowmee.com) | 공개 근거 실측 |
| 언니의파우치 | 운영팀 수동 등록 + 사용자 앱 내 '문의하기' 제보 | 공개 근거(스토어 설명) |
| 올리브영 | 자체 커머스 — 입점(셀러 등록) 프로세스가 곧 DB | **추론** |

- **화해**: 포브스코리아 인터뷰 — 창업 초기 서적으로 성분을 공부해 「소비자가 주의해야 할 성분 20가지」를
  수작업 정리, 기사 시점 기준 「9,000개 브랜드 87,000개 제품 중 70,000개 분석」·「국내에 화장품 데이터를
  우리만큼 축적한 곳은 없다」(이웅 대표) ([기사](https://www.forbeskorea.co.kr/news/articleView.html?idxno=314371)).
  현재는 화해 비즈니스 채널에 「제품 등록/수정 프로세스」가 공식 문서화 — 브랜드가 엑셀 양식 파일 + 필요서류를
  화해제품운영팀(request@birdview.kr)에 이메일 제출 ([화해 비즈니스 안내](https://business.hwahae.co.kr/hwahae-tips/product-registration-on-hwahae-app) —
  조사 시점 원문 페이지는 이동(404), 내용은 검색 캐시로 확인). 채용 정보에서도 「25만 개 전 성분 포함 제품 정보」를
  자산으로 명시 — 성분 데이터가 곧 해자라는 뜻이고, 그 해자는 **수년간의 운영 인력 투입**으로 만들어졌다.
  *(미확인: 초기 7만 건을 크롤링했는지 전량 수작업이었는지는 공개 근거 없음)*
- **글로우픽**: 공개 등록 페이지 원문 확인 — 「상단 파일 다운로드 받아 가이드 확인 후 템플릿 기재하여 제품
  누끼컷과 함께 db@glowmee.com 으로 메일 발송」, 등록 대상은 「아직 글로우픽 앱 내에 제품 정보가 없는 브랜드 및
  제품」 ([글로우픽 DB 등록 안내](https://glowpickad.oopy.io/6da775c0-0d7b-403a-8d9d-8b5fb9c333e6)).
  브랜드가 마케팅 노출을 원해서 **자발적으로 데이터를 바치는** 구조 — 플랫폼 파워가 전제다.
- **언니의파우치**: 플레이스토어 설명 — 「운영팀은 지속적으로 새로운 화장품을 등록해오고 있습니다. 만약 없어진
  화장품이 있다면 앱 내 문의하기를 통해 말씀해주시면」 ([스토어](https://play.google.com/store/apps/details?id=com.ui.monyapp)) —
  운영팀 수작업 + 사용자 제보 크라우드소싱.

**교훈(facefit에 적용)**: 업계 선두조차 전 제품 공적 DB가 없어서 ① 운영 인력 수작업 ② 브랜드 셀프 서브미션
③ 사용자 제보, 셋의 조합으로 푼다. 셋 다 「사람이 계속 붙는 운영」이고, 브랜드 서브미션은 플랫폼 파워가
전제라 개인 사이드 프로젝트에는 성립하지 않는다. 개인·서버 0이 가져올 수 있는 유일한 등가물은 **③의 개인화
버전 — 사용자가 자기 제품을 자기 기기에 직접 등록**하는 것뿐이다. 기록 앱은 검색 앱과 달리 이걸로 충분하다:
사용자는 "전 세계 제품"이 아니라 **자기 화장대 위 5~15개**만 필요하다.

## facefit 다음 계단 후보

### 하는 안 — 커스텀 제품 로컬 등록 (권장)

- 자동완성에서 미스나면 「직접 등록」 폴백: 제품명(+선택: 브랜드·카테고리)을 입력해 로컬(기기) 저장,
  이후 기록·자동완성에 기능성 DB 히트와 동일하게 노출.
- 근거: ① 무료 경로 전멸(위 평가표) ② 업계 표준이 결국 수동 입력의 변형(질문 2) ③ 서버 0·비용 0·약관
  리스크 0 ④ 기록 앱의 실요구(자기 제품 5~15개)에 정확히 닿는다.
- 비용: 입력 폼 + 로컬 저장 + 검색 인덱스 병합 — v2-2 검색 인프라 위에 작게 얹힌다.

### 안 하는 안 (보류 목록)

- **코리안넷 단가 문의**: 선행 결론 유지 — 커스텀 등록이 돌아간 뒤에도 커버리지 불만이 실측되면 그때.
  바코드 스캔 UX까지 세트로 가야 값을 해서 개인 수지에 안 맞을 공산이 크다.
- **네이버 API HUB(NCP) 추적**: 쇼핑 검색이 부활하면 재평가 — 현재는 종료 상태이고 부활 신호 없음.
- **OBF 기여/연동**: 한국 커버리지가 자라기 전에는 무의미. 실측 수치(한글 0/5)가 판단 근거.
- **블로그·웹문서 검색 우회(카카오)**: 정형 메타 부재로 카드 표시 요구 미달 — 품질 대비 복잡도 손해.
