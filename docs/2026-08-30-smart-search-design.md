# v2-3 설계 — 똑똑한 검색: 브랜드+제품명 자연어 검색 (2026-08-30)

> 근거: [v2-2 설계](2026-08-29-product-api-design.md)(§3-2 2요청 최신순·무음 실패 / §4-1 파서·
> `keepsSnapshot` 토큰 규칙 / §2-3 API 실측) · 세션 실측 5건(2026-08-30, §2에 전재).
> 사용자 요구(원문): 「내가 원한 건 내가 쓰는 제품명을 치면 그 제품이 뜨는 거였어.」 —
> 「토리든 다이브인 세럼」처럼 **브랜드+제품명 자연어**로 쳐도 그 제품이 떠야 한다.
> 현재는 보고 품목명의 연속 부분문자열만 맞는다(「토리든」 0건 — 품목명에 브랜드가 없다).

---

## 0. 결론 요약

- **앵커 사다리 + 클라 대조를 채택한다.** 쿼리를 공백 토큰으로 쪼개 **최장 토큰부터**
  `item_name`으로 API를 부르고(0건이면 다음 토큰, 최대 3회), 잡힌 결과를 **전체 토큰이
  `ITEM_NAME` 또는 `ENTP_NAME`에 부분문자열로 들어가는지**로 걸러 낸다. 실측 조합
  (§2-4: 「다이브인」 17건 + 각 결과에 `ENTP_NAME` 동봉)이 이 설계의 성립 근거다.
- **대조 술어는 한 벌이다.** 검색 필터와 `keepsSnapshot`(이름 수정 시 스냅샷 유지 판정)이
  **같은 정규화·같은 토큰 규칙**(소문자화·공백 제거·토큰 부분문자열)을 공유한다 — 규칙이
  두 벌이면 드리프트한다. 겸사겸사 `keepsSnapshot`에 `ENTP_NAME`을 OR로 넣어
  「토리든 세럼」식 브랜드 포함 줄여 쓰기도 스냅샷을 유지하게 된다(§3-3).
- **(주)·주식회사 접두어 처리는 안 만든다** — 부분문자열 대조가 이미 흡수한다
  (「토리든」 ⊂ 「(주)토리든」). 별칭 사전·접두어 스트리핑은 YAGNI(§3-2).
- **최신순 창은 이원화한다**(§3-4): 다중 토큰이고 앵커 totalCount ≤ 30이면 **전수
  (numOfRows=T, pageNo=1)**를 받아 정확 대조, > 30이면 마지막 페이지(numOfRows=30)만.
  **단일 토큰은 현행(2요청·numOfRows=10) 그대로다** — 하위 호환 0 변경.
- **전수 창에서 대조 생존 0이면 앵커 결과를 그대로 보여 준다**(§3-5) — 하우스 브랜드
  (설화수→(주)아모레퍼시픽)처럼 브랜드 토큰이 업소명에 안 맞는 한계(§2-5)를 무음 0건이
  아니라 「앵커가 찾은 그 제품들」로 흡수한다. 광역 창(T>30)의 생존 0은 무음 []다.
- 쿼터 산수: 검색 1회 = **1~4요청**(단일 토큰 1~2 — 현행 동일 · 다중 토큰 프로브 1~3 +
  본문 0~1). 등록 1회 ≈ 8~18요청(현행 6~10) → 일 10,000회로 **등록 550회+/일** 여유(§3-6).
- placeholder는 「예: 토리든 다이브인 세럼」으로 교체 — 예시 자체가 검색 축을 가르친다.
  「브랜드로 검색돼요」류 약속 문장은 안 쓴다(하우스 브랜드 한계가 있어 과약속이다)(§3-7).

## 1. 목표 · 비목표

**목표**: 「브랜드 제품명」 꼴 자연어 쿼리(공백 포함·브랜드 토큰 포함)가 그 제품을 제안에
띄운다. 단일 토큰 검색·수기 등록·무음 실패·명시 탭 부착·스냅샷 규칙은 지금 그대로다.
그것뿐이다.

**비목표(YAGNI — §6 보류 목록에 이유)**: `getRptEntpInq` 2단 검색(업체→품목 브리지가
API에 없다 — §2-3 실측으로 원천 불가) · 브랜드→법인 별칭 사전 · 형태소 분석·초성 검색 ·
오타 교정 · 검색 결과 캐싱 · 비기능성 제품 커버리지(식약처 소스 밖 — 별도 리서치 진행 중,
이 설계는 식약처 소스 안에서의 검색 품질만 다룬다).

## 2. 실측 근거 (세션 실측 2026-08-30 — 이 위에서 설계했다, 재실측 불필요)

1. **`item_name` LIKE는 연속 부분문자열만** — 보고 품목명엔 공백이 없어서
   (「다이브인저분자히알루론산수분버블세럼」) 공백 든 쿼리(「다이브인 세럼」)는 0건이다.
   → 쿼리를 통째로 보내는 현행 경로는 다중 토큰에서 구조적으로 0건이다.
2. **품목 조회 API(getRptPrdlstInq)는 업체 필터가 없다** — 미문서 파라미터
   `entp_name`·`entp_seq`를 실측했으나 무시된다(totalCount 불변).
3. **getRptEntpInq(업체 조회)는 업체 정보만 반환** — 「토리든」 → (주)토리든
   (ENTP_SEQ 20153195)은 잡히지만 품목 목록을 안 준다. **업체→품목 브리지 없음** —
   2단 검색(브랜드로 업체 찾고 그 업체의 품목 받기)은 API 차원에서 불가능하다.
4. **성립 확인된 조합**: `item_name=다이브인` → 17건, 각 결과에 `ENTP_NAME`이 실려 온다
   (대부분 (주)토리든). 즉 **한 토큰으로 검색하고 나머지 토큰을 클라이언트에서
   품목명+업소명에 대조하면** 「토리든 다이브인 세럼」이 정확히 그 제품들로 좁혀진다.
   실응답은 스크래치패드 `entp-toriden.json` 등 — 태스크 0에서 픽스처화한다.
5. **한계**: 브랜드명≠법인명인 대기업 하우스 브랜드(설화수→(주)아모레퍼시픽)는 브랜드
   토큰이 업소명에 안 맞을 수 있다 — §3-5의 폴백이 흡수 범위, §7-1이 잔여 리스크다.

현 코드 실태(v2-2 라이브): `searchProducts`는 쿼리 원문을 `item_name`에 실어
①totalCount ②마지막 페이지(numOfRows=10)의 2요청·역순. `parseItems`는 순수 파서
(취하 제외·effects·PA 정규화). `keepsSnapshot(name, itemName)`은 이름 토큰 전부가
정규화된 품목명에 부분문자열이면 유지. `Products.tsx`는 300ms 디바운스 + AbortController +
`settledName`(고른 직후 재검색 억제).

## 3. 결정 사항 (대안 비교)

### 3-1. 앵커 선택 — 최장 토큰 우선 사다리 ✅

쿼리 토큰 중 **어느 하나**를 `item_name`으로 보내야 한다(§2-1: 통째로는 0건, §2-2: 업체
필터 없음). 후보 비교:

| 대안 | 요청 수 | 앵커 품질 | 판정 |
|---|---|---|---|
| **A. 최장 토큰 우선, 0건이면 다음 토큰(길이순), 최대 3회** | 프로브 1~3 | 긴 토큰일수록 부분문자열 매치가 적다 — 최장 ≈ 최소 totalCount의 근사다(「다이브인」 17건 vs 「세럼」 수만 건) | ✅ **채택.** 대부분 프로브 1회에 명중하고, 브랜드가 최장인 쿼리(「라로슈포제 세럼」)만 사다리를 탄다 |
| B. 전 토큰 프로브 후 최소 totalCount 앵커 | 항상 토큰 수만큼(+1) | A보다 근소 우위 | 기각 — A가 같은 앵커를 대개 1회에 집는다. 항상 3~4요청을 내는 대가로 얻는 것이 거의 없다 |
| C. 첫 토큰 고정 | 1 | ❌ 한국어 쿼리는 브랜드가 앞이다(「토리든 다이브인」) — 첫 토큰이 0건의 주범 | 기각 |
| D. 토큰별 각각 검색 후 교집합 | 토큰 수 × 2 | 브랜드 토큰이 0건이라 교집합이 공집합 | 기각 — §2-1 실측이 원천 봉쇄 |

- **앵커 후보 = 길이 2자 이상 토큰만, 길이 내림차순, 최대 3개.** 1자 토큰은 194,754건
  전집에서 앵커 가치가 없고(광역 totalCount → 창 대조 생존 0), 사다리가 1자에서 멈추면
  더 나은 토큰에 영영 못 간다. 기존 「2자 미만 미검색」 규칙과 결이 같다. 후보가 0개면
  요청 없이 `[]`.
- 같은 길이 토큰은 앞선 것부터(안정 정렬) — 동률 규칙에 머리를 더 쓰지 않는다.
- 사다리 전부 0건이면 `[]` — 무음 원칙 그대로(프로브 요청 ≤ 3으로 상한).
- 프로브는 현행 2요청 전략의 ①(numOfRows=1 totalCount)과 **같은 호출**이다 — 사다리는
  새 요청 종류가 아니라 ①의 반복이다. 모든 요청에 기존 `AbortSignal` 그대로 전파.

### 3-2. 클라 대조 규칙 — 술어 한 벌, 필드별 OR ✅

**규칙: 쿼리의 모든 토큰이, 정규화된(소문자화·공백 제거) `ITEM_NAME` 또는 `ENTP_NAME`
어느 한쪽에 부분문자열로 들어가면 생존.** 앵커 토큰도 예외 없이 같은 규칙을 탄다
(LIKE로 잡혔으니 자명 통과 — 특례 코드가 없는 편이 싸다).

| 결정 지점 | 채택 | 기각 대안과 이유 |
|---|---|---|
| 정규화 | **`keepsSnapshot`과 동일 규칙 공유**(소문자화 · 원본 쪽 공백 제거 · 쿼리 쪽 공백 토큰화) — 유틸 함수로 추출해 양쪽이 임포트 | 별도 규칙 신설 — 규칙이 두 벌이면 「검색에선 잡히는데 수정하면 스냅샷이 떨어지는」 드리프트가 조용히 생긴다 |
| 두 필드 결합 | **필드별 OR**: `norm(itemName).includes(t) \|\| norm(entpName).includes(t)` | 두 필드를 이어 붙인 한 문자열 대조 — 토큰이 필드 경계를 가로질러 우연 매치하는 오염(「…세럼」+「(주)로제…」에 「럼주」가 매치)이 생긴다. OR 두 번이 더 싸고 정확하다 |
| 법인 접두어((주)·주식회사) | **처리 안 함** | 스트리핑·별칭 사전 — 부분문자열 대조가 「토리든」 ⊂ 「(주)토리든」을 이미 흡수한다. 사용자가 「주식회사토리든」을 칠 일은 없다(YAGNI) |

오판 방향(§7-2에 재론): 과소 대조(우연 부분문자열 — 업소명 「세럼코스메틱」에 토큰
「세럼」 매치)의 피해는 **제안 한 줄 노이즈**뿐이다(각 제안 줄에 품목명+업소명이 이미
보이므로 사용자가 안 고르면 끝). 과잉 대조(정당한 제품이 걸러짐)가 진짜 리스크이고
§3-5의 폴백이 그 안전판이다.

### 3-3. `keepsSnapshot` 확장 — 같은 술어에 `ENTP_NAME` 편입 ✅

대조 유틸을 한 벌로 만들면 `keepsSnapshot`도 공짜로 좋아진다: **유지 판정을
「토큰 전부가 원본 품목명 또는 업소명에 포함」으로 넓힌다**(시그니처
`keepsSnapshot(name, snapshot)` — 스냅샷에 `entpName`이 이미 박제돼 있다, v2-2 §3-3).

- 살아나는 정상 사용: 브랜드 검색으로 고른 제품을 「토리든 세럼」으로 줄여 쓰기 —
  현행은 「토리든」 ∉ 품목명이라 스냅샷이 떨어진다(브랜드 검색이 생기는 순간 이 줄여
  쓰기가 흔한 패턴이 된다).
- 갈아치우기 방어는 그대로: 「나이아드 세럼」은 「나이아드」가 품목명·업소명 어디에도
  없어 여전히 떨어진다. 기존 테스트의 떨굼 케이스 전부 유지된다(OR 확장은 유지 방향으로만
  넓힌다).
- 새 오판 여지: 이름을 브랜드 토큰만으로(「토리든」) 갈아치우면 같은 회사의 **다른** 제품
  이름일 때도 스냅샷이 산다 — 피해는 같은 회사 뱃지의 오표시 하나이고, v2-2 §3-2가
  「조건을 늘릴수록 규칙만 어려워진다」로 수용한 것과 같은 등급이다.

### 3-4. 최신순 창 — 다중 토큰만 이원화, 단일 토큰 현행 유지 ✅

대조로 걸러 내면 마지막 페이지 10건의 생존이 0일 수 있다 — 창 크기의 트레이드오프
(레코드당 `EE_DOC_DATA` 포함 ~2.7kB):

| 대안 | 요청 | 응답 크기 | 제안 품질 | 판정 |
|---|---|---|---|---|
| A. 현행 그대로(numOfRows=10 마지막 페이지) | +0 | ~27kB | ❌ 잔여 1~10건에서 대조 → 생존 0이 잦다(창이 좁은데 필터까지 얹는다) | 기각 |
| **B. T ≤ 30이면 전수(numOfRows=T, pageNo=1) / T > 30이면 마지막 페이지(numOfRows=30)** | +0 | ≤ ~81kB | 전수 창이면 **대조가 정확하다**(앵커가 잡은 걸 하나도 안 놓친다). 광역 앵커는 최신 1~30건 창 — 수용 | ✅ **채택** — 목표 케이스(제품 라인명 앵커, 「다이브인」 17건)가 정확히 T ≤ 30 구간이다 |
| C. numOfRows=50~100 | +0 | 135~270kB | B 대비 광역 앵커에서 창이 조금 넓어질 뿐 | 기각 — 디바운스마다 나가는 응답이라 모바일에서 비싸고, 광역 앵커의 생존율은 창 크기가 아니라 앵커 선택의 문제다 |
| D. 뒤에서 여러 페이지 워크(생존 10건까지) | +1~K | K × 27kB | 최고 | 기각 — 요청 수가 데이터 분포에 좌우돼 상한을 못 잡는다. B의 전수 창이 목표 케이스를 이미 정확히 덮는다 |

- **단일 토큰(공백 없는 쿼리)은 현행 그대로**(①totalCount ②numOfRows=10 마지막 페이지) —
  하위 호환 요구의 명시 이행. 기존 `searchProducts` 테스트가 무변경으로 통과해야 한다.
  (전수 창을 단일 토큰에도 펴면 v2-2의 「잔여 출렁임」 천장도 고쳐지지만, 디바운스마다
  응답이 3배가 되고 라이브 경로의 거동이 바뀐다 — 필요가 실측되면 그때 통일한다, §6.)
- 대조·역순 후 **제안은 10건으로 자른다**(전수 창은 최대 30건이 나온다) — UI 밀도 유지.
- T > 30 마지막 페이지의 잔여 출렁임(1~30건)은 v2-2 §3-2와 같은 수용이다.

### 3-5. 대조 생존 0의 처리 — 전수 창은 앵커 결과 폴백, 광역 창은 무음 [] ✅

하우스 브랜드 한계(§2-5)가 정확히 여기서 터진다: 「설화수 자음생크림」은 앵커
「자음생크림」이 제품들을 **정확히 잡는데**, 토큰 「설화수」가 품목명에도
업소명((주)아모레퍼시픽)에도 없으면 대조가 전멸시켜 0건이 된다 — 필터가 검색을 현행보다
**나쁘게** 만드는 유일한 경로다.

| 창 | 생존 0이면 | 근거 |
|---|---|---|
| **전수(T ≤ 30)** | **앵커 결과를 대조 없이 그대로 표시**(역순·10건 컷) | 전수 창에서 대조 전멸 = 나머지 토큰이 식별에 기여 못 한 것(하우스 브랜드·별명). 앵커 자체가 이미 강한 식별자(전집에서 ≤30건)라 앵커 결과가 곧 정답 후보다. 각 제안 줄에 업소명이 보이므로 사용자가 최종 판별한다 |
| 광역(T > 30) | 무음 `[]` | 광역 앵커(「세럼」)의 최신 30건은 쿼리와 무관한 제품 도배다 — 보여 주는 것이 0건보다 나쁘다(사용자 요구가 「내 제품이 뜨는 것」이지 「아무거나 뜨는 것」이 아니다). 무음 실패 원칙 그대로 |

폴백은 추가 요청 0(이미 받은 본문의 재사용)이고, 무음 원칙(에러 UI 없음)과 충돌하지
않는다 — 실패를 알리는 게 아니라 덜 좁힌 결과를 주는 것이다.

### 3-6. 쿼터 산수·디바운스 ✅

- 검색 1회: 단일 토큰 = 1~2요청(0건이면 1 — 현행 동일). 다중 토큰 = 프로브 1~3 +
  본문 0~1 = **1~4요청**(상한 4, 사다리 캡이 보장).
- 등록 1회: 디바운스 통과 쿼리 ≈ 4~6회. 타이핑 전반부는 단일 토큰(첫 단어 입력 중 —
  2요청), 후반부만 다중 토큰(2~4요청) → **등록 1회 ≈ 8~18요청**(현행 6~10 대비 +30~80%).
- 일 10,000회 ÷ 18 ≈ **등록 550회+/일** — 현 규모(개인 사용 수준)에서 여유가 크다.
  소진 시 거동은 현행과 동일(무음 폴백 → 수기 등록), 대응도 동일(운영계정 증액은 보류 —
  v2-2 §6).
- 디바운스(300ms)·`AbortController`·`settledName`(고른 직후 재검색 억제)은 **무변경** —
  사다리의 프로브들도 같은 signal을 물고 함께 취소된다. 브랜드 우선 타이핑 구간
  (「토리든 다…」)에서 앵커 후보 2자 게이트가 1자 토큰 프로브를 걸러 쿼터 낭비를 막는다
  (「토리든」 0건 1요청으로 끝).

### 3-7. placeholder — 예시 교체, 약속 문장 제거 ✅

현행 「예: 수분 토너 (제품명으로 검색돼요)」는 v2-2의 기대치 설계(브랜드 0건이 정상)였다 —
이번 계단이 그 전제를 뒤집으므로 낡는다. 게다가 예시 「수분 토너」는 공백 쿼리라 현행
구현에서 정작 0건이 나는 자기모순도 있었다.

- **채택: 「예: 토리든 다이브인 세럼」** — 예시 자체가 「브랜드+제품명」 검색 축을
  가르친다. 괄호 설명은 뗀다.
- 「브랜드로 검색돼요」류 **약속 문장은 쓰지 않는다** — 하우스 브랜드 한계(§2-5)가 있어
  약속하면 거짓이 되는 케이스가 실재한다. 예시는 약속이 아니라 시범이다(문구 규율 —
  v1 §5-3의 단정 금지와 결이 같다).
- 실브랜드 표기 리스크: placeholder에 특정 상표(토리든)를 쓰는 것은 사실 예시이지 광고·
  제휴 암시가 아니다 — 그래도 검수 민감이 걱정되면 가상 브랜드 대신 **실검색이 되는
  예시여야 가르침이 성립**하므로 유지한다(검수 반려가 실측되면 그때 일반 명사 예시로
  후퇴 — 그 판단은 반려 사유가 입력이다).

## 4. 설계 (모듈별)

### 4-1. `logic/mfds.ts` — 대조 유틸 추출 + 앵커 사다리

```ts
/** 정규화·대조 한 벌(§3-2) — 검색 필터와 keepsSnapshot이 같이 쓴다. */
const norm = (s: string) => s.replace(/\s+/g, '').toLowerCase();
const tokenize = (s: string) => s.toLowerCase().split(/\s+/).filter(Boolean);

/** 토큰 전부가 품목명 또는 업소명(필드별 OR — 경계 오염 방지)에 부분문자열이면 참. */
function hasAllTokens(tokens: string[], itemName: string, entpName: string): boolean;

/** 시그니처 변경: (name, itemName) → (name, snapshot). 판정은 hasAllTokens 위임(§3-3). */
export function keepsSnapshot(name: string, snapshot: Pick<MfdsSnapshot, 'itemName' | 'entpName'>): boolean;

/** 시그니처 불변. 내부만 앵커 사다리로 확장(§3-1·3-4·3-5). */
export function searchProducts(query: string, signal: AbortSignal, fetchFn?: typeof fetch): Promise<Suggestion[]>;
```

`searchProducts` 내부 흐름(의사코드):

```
tokens = query.trim().split(/\s+/)          // ⚠️ API로 나가는 앵커는 원문 케이스 그대로 —
                                            //    API LIKE의 영문 대소문자 감도는 미실측이라
                                            //    소문자화는 클라 대조(hasAllTokens) 안에서만 한다
if (tokens.length === 1)                    // 단일 토큰 — 현행 경로 그대로(§3-4)
  probe → T<1이면 [] → 마지막 페이지(rows=10) → parse → reverse
else                                        // 다중 토큰 — 신설 경로
  anchors = tokens.filter(len ≥ 2) 길이 내림차순 slice(0, 3)
  for anchor of anchors:
    T = probe(anchor)                       // rows=1 — 현행 ①과 같은 호출
    if (T ≥ 1):
      body = T ≤ 30 ? page(rows=T, pageNo=1)               // 전수 창
                    : page(rows=30, pageNo=ceil(T/30))     // 광역 창(마지막 페이지)
      all = parseItems(body).reverse()
      hit = all.filter(s => hasAllTokens(tokens, s.itemName, s.snapshot.entpName))
      return (hit.length ? hit : (T ≤ 30 ? all : [])).slice(0, 10)   // §3-5 폴백
  return []                                 // 사다리 전멸 — 무음
```

- `parseItems`·`page`(봉투 방어·resultCode 판정·URLSearchParams)·무음 실패 규약은
  **무변경 재사용** — 실패는 전 경로에서 여전히 `[]`로 수렴한다.
- 프로브·본문 요청 전부에 기존 `signal` 전파(사다리 도중 취소 즉시 중단).

### 4-2. `Products.tsx` — 변경 2곳뿐

- `keepsSnapshot(name.trim(), snapshot.itemName)` → `keepsSnapshot(name.trim(), snapshot)`
  (§3-3 시그니처 변경 추종).
- placeholder 「예: 수분 토너 (제품명으로 검색돼요)」 → 「예: 토리든 다이브인 세럼」(§3-7).
- 디바운스·제안 리스트·`settledName`·명시 탭 부착·카드 메타는 **전부 무변경** — 제안
  줄이 이미 품목명+업소명을 보여 주므로 폴백 결과(§3-5)의 판별 재료도 이미 화면에 있다.

### 4-3. 하위 호환 체크리스트 (불변 계약)

- 단일 토큰 쿼리: 요청 패턴(①rows=1 ②rows=10 마지막 페이지)·결과·역순 **동일** —
  기존 `searchProducts` 테스트 무수정 통과가 판정 기준이다. **예외 1건**: 인코딩 테스트
  (「검색어와 서비스키를 인코딩해 싣는다」)는 쿼리가 「수분 토너」 — 다중 토큰이라 신설
  경로를 타 `item_name`이 앵커(「수분」)로 바뀐다. 이 테스트의 목적은 인코딩 검증이므로
  쿼리를 단일 토큰으로 바꿔 유지한다(거동 퇴행이 아니라 검증 대상의 재지정이다 —
  공백 쿼리를 통째로 보내던 현행 거동 자체가 0건 나는 결함이었다, §2-1).
- 무음 실패: 신설 경로의 모든 실패(프로브 실패·본문 실패·사다리 전멸)가 `[]` — 에러 UI 없음.
- 명시 탭 부착: 폼 로직 무변경이라 자동 성립.
- `keepsSnapshot`: 기존 유지 케이스 전부 유지·기존 떨굼 케이스 전부 떨굼(OR 확장은
  유지 방향 단조 — 기존 테스트에 `entpName` 인자만 보태 무결과 통과).

## 5. 태스크 분해 (TDD — Red 먼저)

0. **픽스처 확보(코드 0)**: 「다이브인」 실응답(17건 — §2-4)을 스크래치패드에서
   `logic/__fixtures__/mfds-divein.json`으로 복사(없으면 실키로 1회 재수집). 다중 토큰
   대조 테스트의 실데이터 입력이다 — 지어낸 봉투로 잠그면 v2-2 픽스처 원칙이 깨진다.
1. **대조 유틸 + `keepsSnapshot` 확장**: 테스트 Red(기존 케이스 전부 시그니처만 바꿔 유지 ·
   **브랜드 줄여 쓰기 「토리든 세럼」 → entpName 「(주)토리든」 매치로 유지** · 갈아치우기
   여전히 떨굼 · 필드 경계 가로지르는 토큰은 불매치(OR이지 연결 문자열이 아님을 잠근다) ·
   영문 대소문자·공백 무시) → `hasAllTokens` 추출·`keepsSnapshot` 위임 구현 →
   `Products.tsx` 호출부 추종.
2. **앵커 사다리**: 테스트 Red(fetch 주입 — **최장 토큰이 첫 프로브** · 0건이면 다음
   토큰 재프로브 · **1자 토큰은 앵커 후보 제외** · 후보 3개 초과는 안 부름 ·
   **사다리 전멸 시 요청 ≤ 3에 `[]`** · 전 요청 signal 전파 · **앵커는 원문 케이스로
   나간다**(소문자화는 대조 안에서만 — §4-1) · 단일 토큰 기존 테스트 무수정 통과(인코딩
   테스트 1건만 쿼리를 단일 토큰으로 갱신 — §4-3 예외)) → 구현.
3. **창 이원화 + 대조 + 폴백**: 테스트 Red(**T ≤ 30 → rows=T·pageNo=1** · T > 30 →
   rows=30·마지막 페이지 · 다이브인 픽스처에서 「토리든 다이브인 세럼」 → 토리든 제품만
   생존(역순·10건 컷) · **전수 창 생존 0 → 앵커 결과 그대로**(하우스 브랜드 시나리오) ·
   **광역 창 생존 0 → `[]`** · 대조 통과가 entpName 쪽 매치로도 성립) → 구현.
4. **placeholder 교체 + 폼 회귀**: 테스트 Red(placeholder 문구 · 다중 토큰 입력 →
   제안 표시 → 탭 → 스냅샷 부착의 통합 경로 1건) → 구현.
5. **문구·릴리스 절차**: 릴리스 노트(「브랜드+제품명으로 검색돼요」는 노트에서도 안 쓴다 —
   「제품 검색이 더 잘 찾아요」 수준의 비약속 서술) → 번들 검수 → 실기기에서
   「토리든 다이브인 세럼」 실호출 확인 → plan/changeLog sweep.

**돌연변이 후보**: 앵커 정렬 제거(첫 토큰 고정 — 브랜드 우선 쿼리가 사다리를 헛돈다) /
사다리 캡 제거(토큰 폭탄 쿼리에 요청 폭주) / 1자 게이트 제거(광역 프로브가 사다리를
조기 종료) / 0건 앵커에 본문 요청(쿼터 — 기존 돌연변이의 사다리판) / `hasAllTokens`에서
entpName OR 누락(**기능 자체 무효** — 브랜드 토큰 전멸) / 필드 연결 문자열 대조(경계
오염 매치) / 전수 창 경계 `T ≤ 30`→`T < 30`(30건짜리 앵커가 광역 취급) / 폴백 제거
(하우스 브랜드 0건 회귀) / 폴백을 광역 창에도(무관 제품 도배) / `slice(0,10)` 제거
(전수 창 30건 도배) / reverse 제거(2008년 도배 회귀) / `keepsSnapshot` 위임 대신 구규칙
잔존(검색은 잡는데 수정하면 스냅샷이 떨어지는 드리프트).

## 7. 리스크 · 미검증 가정

1. **광역 앵커 × 하우스 브랜드 = 여전히 0건** — 「설화수 크림」(브랜드 + 2자 카테고리)은
   앵커 「설화수」 0건(품목명에 없으면) → 「크림」 광역 → 최신 30건에 설화수 없음 →
   생존 0 → 무음 []. 전수 폴백(§3-5)의 사각이다. 증상은 현행과 동일한 0건(퇴행 아님)이고,
   제품 라인명을 한 토큰이라도 치면(「설화수 자음생」) 벗어난다. 빈도가 실측되면 별칭
   사전(§6)을 꺼낸다.
2. **과소 대조(우연 매치) 방향** — 짧은 토큰이 업소명에 우연히 포함(「세럼」 ⊂
   「세럼코스메틱」)돼 무관 제안이 한 줄 섞일 수 있다. 피해 = 노이즈 한 줄(제안에 업소명
   병기라 판별 가능), 방치 수용.
3. **품목명 내 브랜드 표기의 비일관** — 「대체로 없다」(§2-1)이지 전무가 아니다. 있는
   레코드는 대조가 더 잘 될 뿐(양방향 OR) — 리스크가 아니라 보너스 방향.
4. **응답 크기 가정** — 레코드당 ~2.7kB는 실측 표본 기준. `EE_DOC_DATA`가 유난히 큰
   레코드군이 있으면 전수 창 30건이 100kB를 넘을 수 있다 — 증상은 제안 지연뿐이고
   디바운스·abort가 연타를 막는다. 거슬리면 창을 20으로 줄인다(상수 하나).
5. **프로브 totalCount의 신선도** — 프로브와 본문 요청 사이에 totalCount가 변하면(신규
   보고 유입) 마지막 페이지 계산이 한 건 어긋날 수 있다 — v2-2부터 있던 성질이고 피해는
   제안 한 건 누락, 수용.
6. **placeholder의 실브랜드 표기** — 검수 반려 가능성 낮음(사실 예시)이지만 0은 아니다.
   반려 시 사유를 입력으로 일반 예시로 후퇴(§3-7) — 코드 밖 문구 한 줄이라 비용 0.
