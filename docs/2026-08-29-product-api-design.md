# v2-2 설계 — 화장품 제품 API 도입 + 제품 표시 개선 (2026-08-29)

> 근거: [화장품 제품 데이터 API 리서치](2026-08-29-cosmetics-data-api-research.md)(단일 출처 —
> 1순위 식약처 기능성화장품 보고품목 API) · [v1 설계](2026-08-29-v1-design.md) §4-2(미지 필드
> 보존) · §5-3(문구 규율) · 서비스 구상 §5-7(제품 검색·자동완성 계단).
> 사용자 요구: 「디자인 개선의 핵심이 제품 표시 — 그 재료로 API를 먼저 도입한다.」
> 즉 **API가 붙고 화면이 바뀌어야** 목적이 달성된다. 이 문서는 둘을 함께 다룬다.

## 0. 결론 요약

- **클라이언트 직호출을 채택한다 — 프록시·스냅샷 없이 성립한다(실측 완료).**
  ① `apis.data.go.kr` 게이트웨이는 **임의 Origin을 그대로 반사해 CORS를 허용**하고(실측 —
  §2-1), ② 앱인토스 미니앱 웹뷰는 **외부 도메인 fetch에 제한이 없다**(공식 문서 실측 — §2-2).
  리서치의 「프록시 없는 동안은 자동완성도 없다」는 전제가 **이 두 실측으로 뒤집혔다** —
  프록시를 기다릴 이유가 사라졌다.
- **서버 0 원칙은 유지된다.** 원칙의 실체는 「우리가 운영하는 서버 0」이다 — v2-1 푸시가
  토스 서버를 빌려 쓰듯, 이번엔 식약처 서버를 빌려 쓴다. 단 **「런타임 네트워크 호출 0」은
  이번에 처음 깨진다** — 검수·온보딩 문구를 함께 갱신한다(§3-5).
- 서비스 키는 번들에 실린다 — **의도된 수용**이다. 무료·읽기 전용 공공데이터라 탈취 피해의
  상한이 「일 10,000회 쿼터 소진 = 그날 자동완성 정지」이고, 그때의 폴백(수기 입력)은 어차피
  커버리지 밖 제품(색조·클렌징류) 때문에 **상시 존재해야 하는 경로**다(§3-1).
- UX는 「이름 입력란 = 검색창」이다. 별도 검색 화면 없이 기존 폼의 이름 칸에 자동완성
  제안이 붙고, 제안을 고르면 브랜드(업소명)·효능 뱃지·SPF/PA가 **스냅샷으로 저장**된다.
  무시하고 타이핑하면 지금 그대로의 수기 등록이다 — 실패·오프라인·커버리지 밖 전부
  이 경로로 조용히 수렴한다(§3-2).
- 효능효과 표기는 **식약처 보고 구분의 인용**으로 한정한다 — 뱃지 문구는 보고 데이터의
  명칭 그대로 + 출처 캡션. 앱이 「효과 있어요」로 재해석하는 순간 화장품법 표시·광고
  규제와 §5-3 규율을 동시에 어긴다(§3-4).

## 1. 목표 · 비목표

**목표**: 제품 등록 시 식약처 보고품목 검색·자동완성이 붙고, 등록된 제품 카드가
브랜드·기능성 뱃지·SPF를 보여 준다. 수기 등록은 지금 그대로 남는다. 그것뿐이다.

**비목표(YAGNI — §6 보류 목록에 이유)**: 프록시 서버 · 성분 사전(원료성분정보) 번들 내장 ·
심사품목 API 병합 · 바코드 · 제품 이미지 · 기존 수기 제품의 소급 API 연결 · 검색 결과
캐싱 · 운영계정 트래픽 증액.

## 2. 조사 결과 (실측 — 추정과 구분해 표기)

### 2-1. data.go.kr CORS — 허용 (실측 ✅)

`curl`로 실제 엔드포인트에 preflight(OPTIONS)와 GET을 임의 Origin으로 보냈다(2026-08-29):

```
OPTIONS https://apis.data.go.kr/1471000/FtnltCosmRptPrdlstInfoService/getRptPrdlstInq
  Origin: https://facefit-web.example
→ 200 OK
  Access-Control-Allow-Origin: https://facefit-web.example   ← 보낸 Origin 그대로 반사
  Access-Control-Allow-Methods: GET,OPTIONS
  Access-Control-Max-Age: 3600
```

GET(더미 키 → 403 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`)에도 같은
`Access-Control-Allow-Origin` 반사가 실렸다 — **에러 응답까지 CORS가 열려 있어 브라우저가
응답 본문을 읽을 수 있다**(키 오류·쿼터 초과를 앱이 판별 가능). HTTPS 지원 ✅(앱인토스
라이브 환경은 HTTPS만 허용 — §2-2와 맞물려 문제없음). 게이트웨이 공통 동작이라
`https://facefit.web.tossmini.com`(실서비스 오리진)도 통과한다고 판단한다 — 단 실서비스
오리진에서의 최종 확인은 태스크 7 실기기 검증에 남긴다.

### 2-2. 앱인토스 외부 네트워크 정책 — 제한 없음 (공식 문서 실측 ✅)

developers-apps-in-toss.toss.im 문서 조회 결과(2026-08-29):

- 「미니앱 WebView 환경에는 일반적인 웹 API 사용이 제한되지 않아요」 — **외부 도메인
  fetch 가능, 콘솔 도메인 허용 목록 등록 절차 없음.**
- 제약은 반대 방향이다: **외부 API 서버 쪽 CORS**가 미니앱 오리진을 허용해야 한다.
  SDK 3.x 오리진은 `https://<appName>.web.tossmini.com`(실서비스) ·
  `https://<appName>.private-web.tossmini.com`(콘솔 QR 테스트). §2-1의 반사형 CORS라
  둘 다 자동 충족된다.
- 라이브 환경은 **HTTPS만 허용**(HTTP 차단 가능) — `apis.data.go.kr`는 HTTPS 제공 ✅.

### 2-3. API 스펙 (data.go.kr 15095680 상세 페이지 실측)

- **엔드포인트**: `https://apis.data.go.kr/1471000/FtnltCosmRptPrdlstInfoService/getRptPrdlstInq`
- **요청**: `serviceKey`(필수) · `item_name`(품목명 검색) · `pageNo` · `numOfRows` · `type=json`
- **응답 필드(발췌)**: `ITEM_NAME`(품목명) · `ENTP_NAME`(업소명 = 책임판매업자 = 사실상 브랜드) ·
  `MANUF_NAME`(제조원) · `REPORT_DATE`(보고일자) · `COSMETIC_REPORT_SEQ`(보고일련번호) ·
  **`EFFECT_YN1~3`**(2호 효능효과: 미백·주름개선·자외선) · `EE_CODE/EE_NAME`(효능효과코드/명) ·
  **`SPF` · `PA`**(자외선차단지수) · `WATER_PROOFING_NAME`(내수성) · `EE_DOC_DATA`(효능효과 자유서술)
- 204,622건 · 무료 · 개발계정 일 10,000회(운영계정은 활용사례 등록 후 증액).
- ⚠️ **추정(미실측)**: ① `item_name`이 부분일치(LIKE)인지 문서에 명시가 없다 — 식약처 계열
  API의 관례상 부분일치로 추정하나, **서비스 키 발급 후 태스크 1에서 실측 확정한다.**
  ② `type=json`의 정확한 응답 봉투 형태(`header/body/items` 구조)도 같은 태스크에서
  실응답 픽스처로 확정한다. 파서는 그 픽스처를 보고 짠다 — 추정으로 코드를 먼저 쓰지 않는다.

### 2-4. 현 코드 실태 (설계가 얹힐 자리)

- `storage.ts`: `Product { id, name, category, startDate, endDate? }` — localStorage,
  **미지 필드 보존 로더**(v1 설계 §4-2가 이번을 위해 미리 깔아 둔 규칙 — 마이그레이션 불필요의
  근거다). 방어 강도 2단계: 필수 필드는 레코드 기각, 표시용 필드는 그 필드만 고쳐 살린다.
- `Products.tsx`: 인라인 폼(이름 text · 카테고리 select · 시작일 date). 이름 칸이 이번
  자동완성의 자리다. 카드 행 = 이름 · 카테고리 칩 · D+n — 메타데이터 줄이 여기 얹힌다.
- `apps-in-toss.config.ts`: 네트워크 관련 플래그 **없음**(webView 3종은 카메라·새로고침용) —
  config 변경 0.
- 콘솔 상세 설명 마지막 줄 「휴대폰에만 저장, 서버 전송 없음」(changeLog 실측) — 이번 계단이
  이 문장을 **부분적으로 낡게 만든다**(§3-5에서 갱신).

## 3. 결정 사항 (대안 비교)

### 3-1. 아키텍처 — 클라이언트 직호출 ✅

| 대안 | 서버 0 | 키 노출 | 검색 품질 | 갱신 | 판정 |
|---|---|---|---|---|---|
| **A. 클라이언트 직호출** | ✅ 유지 | 번들 노출(수용 — 아래) | 원본 그대로(20만 건 전수) | 항상 최신 | ✅ **채택** — CORS·앱인토스 정책 실측이 둘 다 열려 있다(§2-1·2-2). 추가 운영물 0 |
| B. 최소 프록시(Cloudflare Workers 무료) | ❌ **첫 운영물 탄생** | 숨김 | 동일 | 동일 | 기각 — 비용 0이어도 계정·배포·장애 지점·잠드는 무료 티어가 생긴다. 직호출이 실측으로 성립하는데 「언젠가 좋을」 이유로 지금 세우는 것은 YAGNI. v2 성분 판독(AI)이 프록시를 **어차피** 만들 때 이관을 재검토(§6) |
| C. 정적 스냅샷 부분집합 | ✅ | 없음 | ❌ 치명 | ❌ 수동 재빌드 | 기각 — **추릴 기준이 데이터에 없다**(판매량·인기 필드 부재. 「최근 보고분」은 스테디셀러를 버리고, 「주요 브랜드」는 선정 자체가 자의적). 20만 건 전체는 이름만 담아도 수 MB 단위로 번들에 못 싣고, 부분집합은 「검색했는데 없다」가 커버리지 한계인지 스냅샷 한계인지 사용자가 구분 못 한다 |

**키 노출의 실질 위험 평가(A의 대가)**: 서비스 키는 번들 문자열로 노출된다. 탈취 시나리오의
피해 상한 = ① 무료 API라 과금 0 ② 읽기 전용 공공데이터라 데이터 유출 0 ③ 남는 것은
**일 10,000회 쿼터 소진뿐**이고, 그날 앱은 자동완성 없는 수기 입력으로 동작한다 — 이 폴백은
커버리지 밖 제품 때문에 어차피 상시 경로다(§3-2). 즉 최악의 날에도 앱은 v1과 동일하게 돈다.
키 재발급도 무료·즉시다. 다만 **레포에 평문 커밋은 안 한다**(GitHub 크롤러가 쿼터를 태우는
건 피할 수 있는 손해다) — `.env.local`의 `VITE_MFDS_KEY`로 주입하고 gitignore(§4-3).

**서버 0 원칙과의 화해**: 이 앱의 원칙은 「운영할 서버를 만들지 않는다」였고 그건 지켜진다.
깨지는 것은 「런타임 네트워크 호출 0」이라는 파생 성질이다 — v2-1 푸시가 토스 인프라를
빌렸듯 이번엔 식약처 인프라를 빌린다. 성질 변화는 숨기지 않고 문구·검수 고지로 드러낸다(§3-5).

### 3-2. 등록 UX — 이름 입력란 = 검색창, 수기 입력이 곧 폴백 ✅

| 대안 | 판정 |
|---|---|
| A. 별도 검색 화면/모달 신설 | ❌ 화면 하나가 늘고, 수기 입력과 검색이 두 동선으로 갈라진다 — 커버리지 밖 제품(색조·클렌징류, 리서치 명시)은 검색 화면에서 「없음」을 보고 되돌아와야 한다 |
| **B. 기존 폼 이름 칸에 자동완성 부착** | ✅ **채택.** 검색과 수기가 **같은 칸**이다 — 제안이 뜨면 고르고, 안 뜨면(커버리지 밖·오프라인·쿼터 소진·API 장애) 그냥 계속 타이핑해 저장한다. 실패가 사용자에게 「실패」로 보이지 않는다 |
| C. 등록 후 카드에서 「API 연결」 버튼 | ❌ 두 단계 조작 — 등록 순간이 제품명을 정확히 아는 유일한 순간이다 |

동작 규칙:

- **≥2자 + 300ms 디바운스**로 `item_name` 검색, 이전 요청은 `AbortController`로 취소.
  제안 최대 10건(`numOfRows=10`), 각 줄 = 품목명 + 업소명(같은 이름의 타사 제품 구분).
- 제안 탭 → 이름 칸에 품목명 채움 + **스냅샷 필드 부착**(§3-3) + 제안 리스트 닫힘.
  이후 이름을 손으로 고치면 스냅샷은 유지한다(품목명이 길어 줄여 쓰는 경우가 정상 사용이다).
- **모든 실패는 무음**: 제안 리스트가 안 뜰 뿐이다. 에러 배너·토스트를 만들지 않는다 —
  촬영 흐름에서 푸시가 그랬듯(v2-1 §3-2), 등록 흐름을 검색이 방해하는 순간 주객전도다.
- **카테고리는 사용자 선택 그대로 유지** — API에 앱 카테고리에 대응하는 필드가 없다(실측 §2-3.
  `COSMETIC_TARGET_FLAG`는 대상 구분이지 제형 분류가 아니다). 자동 유추(자외선→선크림)는
  이중·삼중 기능성 제품(미백+주름+자외선 에센스 등)에서 오분류를 만든다 — 안 한다.

### 3-3. 데이터 모델 — 등록 시점 스냅샷, 재조회 없음 ✅

```ts
// storage.ts — Product에 선택 필드 1개 추가
export type MfdsSnapshot = {
  reportSeq: string;   // COSMETIC_REPORT_SEQ — 중복 제안 구분·향후 재조회 열쇠
  entpName: string;    // ENTP_NAME(업소명) — 카드의 「브랜드」 줄
  effects: string[];   // EFFECT_YN1~3에서 세운 표기: '미백' | '주름개선' | '자외선차단'
  spf?: string;        // SPF (있을 때만, 원문 그대로 — '50+' 등)
  pa?: string;         // PA (있을 때만)
  fetchedAt: string;   // 'YYYY-MM-DD' — 이 정보가 언제 것인지(스냅샷 원칙의 정직한 표기)
};

export type Product = {
  /* 기존 5필드 그대로 */
  mfds?: MfdsSnapshot;  // 없으면 수기 제품 — v1 데이터 전부가 이 상태다
};
```

- **마이그레이션 0**: 선택 필드 하나라 기존 레코드는 손대지 않고, v1의 미지 필드 보존
  로더(§2-4)가 이미 왕복을 보장한다 — v1 설계 §4-2가 이번을 위해 깔아 둔 규칙이 그대로 회수된다.
- **revive 검증 등급은 「표시용」**: `mfds`의 형태가 어긋나면(필드 누락·타입 오류)
  **`mfds`만 버리고 레코드는 살린다** — category 강등과 같은 등급이다. 제품 기록(이름·기간)이
  본체고 API 메타는 장식이다.
- **재조회 없음(스냅샷 원칙)**: 등록 순간의 응답을 저장하고 끝이다. 열람 시 API를 다시
  부르면 오프라인에서 카드가 깨지고, 호출 0이던 열람 경로에 네트워크가 스민다. 보고 데이터는
  사실상 불변(보고 이력)이라 스냅샷 부패 리스크도 낮다 — `fetchedAt`으로 시점만 정직하게 남긴다.
- 수기 제품과의 공존: `mfds` 유무가 유일한 구분이다. 정렬·활성 판정·타임랩스 구간 바 등
  기존 로직은 `mfds`를 모른다 — 변경 0.

### 3-4. 효능효과 표기 — 「보고 구분의 인용」으로 한정 ✅

화장품법상 표시·광고 규제 민감 영역이라 경계를 명시한다:

- **표시하는 것**: 식약처에 보고된 기능성 구분(미백·주름개선·자외선차단)을 **명칭 그대로**
  뱃지로, SPF/PA를 **원문 수치 그대로**. 카드·상세에 출처 캡션 한 줄:
  「식약처 기능성화장품 보고정보 기준」. 이것은 공적 사실의 인용이다 — 보고 구분은
  식약처가 부여한 법정 분류라 앱이 지어낸 효능 주장이 아니다.
- **표시하지 않는 것**: ① `EE_DOC_DATA`(효능효과 자유서술) — 제조사 서술을 그대로 실으면
  앱이 광고 문구의 전달자가 된다. ② 앱의 재해석 — 「미백에 효과 있어요」「이 제품으로
  밝아져요」류 문장 일절 금지. 뱃지는 명사(분류명)로만 서고, 문장을 만들지 않는다.
- v1 §5-3 규율(단정 금지·질문형)과의 관계: §5-3은 **사용자의 피부 변화**에 대한 단정을
  금지한다. 이번 표기는 **제품의 보고 이력**이라는 별개 축이고, 거기서의 규율은
  「인용 + 출처」다. 두 축이 섞이는 문장(「자외선차단 제품을 쓰니 좋아졌네요」)이 최악이다 —
  카피 리뷰 항목으로 태스크에 박는다.

### 3-5. 검수·프라이버시 문구 갱신 ✅

「런타임 네트워크 호출 0」이 깨지므로 낡는 문장을 능동적으로 고친다:

- **여전히 참**: 사진·관찰·제품 기록은 기기에만 저장, 어디로도 전송 안 됨 — `LOCAL_ONLY`
  문구는 그대로 유효하다(사진 이야기다).
- **갱신할 것**: ① 콘솔 상세 설명 「서버 전송 없음」 → 「사진과 기록은 휴대폰에만 저장돼요.
  제품 검색 시에만 식약처 공공 데이터를 조회해요」 ② 온보딩 프라이버시 항목에 같은 취지
  한 줄 ③ 릴리스 노트에 「제품 검색: 식약처 공공 API 조회(검색어 외 전송 없음, 개인정보
  미포함)」 명기 — 검수자가 네트워크 호출을 발견하고 묻기 전에 먼저 말한다.
- 전송되는 것의 전부 = 사용자가 이름 칸에 친 검색어(제품명). 개인정보가 아니다 —
  그래도 고지한다(고지 비용 0, 신뢰 이득 전부).

## 4. 설계 (모듈별)

### 4-1. `logic/mfds.ts` (신설) — 파서 + 검색 함수

```ts
export const MFDS_ENDPOINT = 'https://apis.data.go.kr/1471000/FtnltCosmRptPrdlstInfoService/getRptPrdlstInq';

/** API 원시 응답 1건 → 제안 1건. 순수 함수 — 태스크 1의 실응답 픽스처가 테스트 입력이다. */
export type Suggestion = { itemName: string; snapshot: MfdsSnapshot };
export function parseItems(json: unknown): Suggestion[];
// 방어 규칙: 봉투 형태가 다르거나 items가 없으면 [] (throw 금지 — 실패는 무음, §3-2).
// 항목 단위로도 방어 — ITEM_NAME 없는 항목만 건너뛴다.

/** fetch 주입(테스트용) + AbortSignal. 실패·비200·파싱 불능 전부 [] — 던지지 않는다. */
export function searchProducts(query: string, signal: AbortSignal, fetchFn?: typeof fetch): Promise<Suggestion[]>;
```

- 키는 `import.meta.env.VITE_MFDS_KEY` — 비어 있으면 `searchProducts`가 즉시 `[]`
  (키 없는 개발 환경·CI에서 앱이 v1처럼 돈다).
- `effects` 조립: `EFFECT_YN1~3`(또는 `EE_NAME` — 태스크 1 픽스처가 확정)에서
  해당 구분명 배열로. 원문 필드가 무엇이든 **저장하는 값은 한글 구분명 3종으로 정규화**한다 —
  카드가 원시 코드를 몰라도 되게.

### 4-2. `Products.tsx` — 폼 자동완성 + 카드 메타

- **폼**: 이름 `<input>` 아래 제안 리스트(카드 안 인라인 — 포털·팝오버 안 만든다).
  `useEffect`(name, 300ms 디바운스, AbortController cleanup) → `searchProducts` →
  제안 state. 제안 탭 → `setName(itemName)` + `snapshot` state 보관 → 저장 시 `mfds` 부착.
  제안 선택 후 이름을 수정해도 스냅샷 유지(§3-2). **선택 없이 저장하면 `mfds` 없음** —
  타이핑 도중 스친 제안이 조용히 붙는 사고를 막는다(명시 탭만이 부착 트리거다).
- **카드(제품 표시 개선의 본체)**: 기존 행 구조 유지 + `mfds` 있으면 메타 줄 추가:
  - 1행(기존): 이름 · 카테고리 칩 · D+n
  - 2행(신설): 업소명(브랜드, `--text-sub`) · 효능 뱃지(기존 `ui.chip` 재사용 — 「미백」
    「주름개선」「자외선차단」) · SPF/PA 칩(「SPF50+ PA++++」)
  - 이미지 슬롯은 **만들지 않는다** — 어떤 소스에도 이미지가 없다(리서치 확정). 텍스트
    구성만으로 서는 카드가 전제이고, 뱃지·칩이 그 밀도를 채운다.
  - 출처 캡션: 목록 하단 1줄 「기능성 표시는 식약처 기능성화장품 보고정보 기준이에요」
    (카드마다 반복하지 않는다 — 소음).
- 수기 제품 카드는 지금과 픽셀 단위로 동일 — 메타 줄 유무만 다르다.

### 4-3. 키 주입 · 설정

- `miniapp/.env.local`: `VITE_MFDS_KEY=<발급 키>` — **gitignore 추가**(레포 평문 방지, §3-1).
  vite가 `VITE_` 접두어를 번들에 인라인한다 — 노출은 §3-1에서 수용한 그대로다.
- `apps-in-toss.config.ts` 변경 0(§2-4 실측 — 네트워크 관련 설정 자체가 없다).
- README에 키 발급 절차 링크 한 줄(빌드 재현용).

## 5. 태스크 분해 (TDD — Red 먼저)

### 5-0. 사용자가 해야 할 일 (코드 밖 — 선행)

1. [공공데이터포털](https://www.data.go.kr) 회원가입(개인).
2. [기능성화장품 보고품목정보(15095680)](https://www.data.go.kr/tcs/dss/selectApiDataDetailView.do?publicDataPk=15095680)
   **활용신청** — 개발계정은 자동승인(즉시). 활용 목적은 「화장품 사용 기록 앱의 제품 검색」
   수준이면 된다.
3. 마이페이지에서 **일반 인증키(Encoding) 확인 후 전달** — 태스크 1의 입력이다.
   (운영계정 전환·트래픽 증액은 보류 — §6. 일 10,000회로 시작한다.)

### 5-1. 구현 태스크

1. **키 스모크 + 가정 실측 (코드 0)** — 발급 키로 curl:
   ① `type=json` 실응답 1건을 **픽스처로 저장**(`logic/__fixtures__/mfds-sample.json` —
   봉투 형태 확정) ② `item_name` 부분일치 여부 실측(「토리든」 같은 브랜드 접두어로 검색)
   ③ `EFFECT_YN`/`EE_NAME`·`SPF`·`PA` 필드 실재·형태 확인. 결과는 이 문서 §2-3에 추기.
   **파서 설계(4-1)의 필드 매핑은 이 실측 후 확정** — 여기서 어긋나면 코드 전에 설계를 고친다.
2. **`logic/mfds.ts` 파서**: 테스트 Red(픽스처 정상 파싱 · 봉투 이상 → `[]` · ITEM_NAME 없는
   항목만 스킵 · effects 정규화 · SPF 없는 제품 → `spf` 부재) → 구현.
3. **`searchProducts` 래퍼**: 테스트 Red(fetch 주입 — 비200 → `[]` · reject → `[]` ·
   abort 전파 · 키 부재 → 즉시 `[]`에 fetch 미호출) → 구현.
4. **storage 확장**: 테스트 Red(`mfds` 왕복 보존 · 형태 이상 시 `mfds`만 제거하고 레코드
   유지 · `mfds` 없는 v1 레코드 무변화) → `MfdsSnapshot` revive 구현.
5. **Products 폼 자동완성**: 테스트 Red(2자 미만 미호출 · 디바운스(fake timers) ·
   제안 표시 · 탭 → 이름 채움 + 저장 시 `mfds` 부착 · 선택 없이 저장 → `mfds` 없음 ·
   `[]` 응답 → 리스트 없음(에러 UI 없음) · 선택 후 이름 수정 → 스냅샷 유지) → 구현.
6. **카드 메타 표시**: 테스트 Red(`mfds` 있으면 업소명·뱃지·SPF 노출 · 없으면 기존과 동일 ·
   출처 캡션 1회) → 구현. **카피 리뷰 체크 포함**(§3-4 — 뱃지가 문장을 만들지 않는가).
7. **문구 갱신 + 릴리스 + 실기기 검증**: 온보딩·콘솔 상세 설명·릴리스 노트 갱신(§3-5) →
   번들 검수 → **실기기(토스 웹뷰, `*.web.tossmini.com` 오리진)에서 검색 실호출 확인**
   (§2-1의 마지막 미실측 고리) → plan/changeLog sweep.

**돌연변이 후보**: 디바운스 제거(매 타이핑 호출 — 쿼터 낭비) / abort 미전파(늦은 응답이
새 검색을 덮음) / `mfds` revive를 레코드 기각으로(메타 오류에 제품 기록 증발) /
빈 키에 fetch 호출(콘솔 403 소음) / 제안 자동 부착(명시 탭 없이 스냅샷이 붙음).

## 7. 리스크 · 미검증 가정

1. **`item_name` 부분일치 여부(최대 가정)** — 미실측(§2-3). 완전일치라면 자동완성 UX가
   성립하지 않는다 → 태스크 1이 **코드 작성 전에** 판정한다. 실패 시 폴백: 심사품목
   API(15056939)의 검색 파라미터를 같은 방법으로 실측하고, 둘 다 안 되면 이 계단을
   보류하고 사용자에게 보고한다(정적 스냅샷으로의 후퇴는 §3-1-C 기각 사유가 그대로 적용).
2. **응답 봉투 형태** — `type=json` 실물 미확인. 태스크 1 픽스처가 파서 테스트의 입력이라
   구조적으로 어긋날 수 없다(픽스처 먼저, 코드 나중).
3. **실서비스 오리진에서의 CORS** — 게이트웨이가 임의 Origin 반사임을 실측했으나(§2-1),
   `*.web.tossmini.com`에서의 최종 확인은 태스크 7 실기기 몫. 어긋나면 증상은 「제안이
   안 뜸」뿐 — 무음 폴백 설계라 사용자 피해 0, 그때 프록시(§6)를 앞당길지 판단.
4. **쿼터 공유** — 일 10,000회는 전 사용자 합산이다. 현 사용자 규모에선 여유가 크지만
   성장 시 소진일이 온다 — 그날의 동작은 v1과 동일(무음 폴백)이고, `push_stats`처럼
   data.go.kr 마이페이지에서 사용량을 볼 수 있다. 소진이 보이면 운영계정 증액(§6)을 꺼낸다.
5. **키 노출** — 의도된 수용(§3-1). 피해 상한 = 쿼터 소진. 재발급 무료·즉시.
6. **data.go.kr 가용성** — 공공 API 특유의 점검 시간대·간헐 지연이 있다. 무음 폴백이라
   등록 흐름은 안 죽는다 — 이 설계의 모든 실패 경로가 같은 곳(수기 입력)으로 수렴하는 이유다.
7. **검수 리스크** — 네트워크 호출이 처음 생기는 번들이다. 릴리스 노트 선제 고지(§3-5)로
   흡수하되, 반려 시 사유가 다음 문구의 입력이다(v2-1 자동검수 대응과 같은 자세).
