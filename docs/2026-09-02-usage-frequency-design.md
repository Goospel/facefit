# v4-2 설계 — 사진에 「이 전에 쓴 것」을 단다: 가끔 쓰는 제품의 실사용 기록 (2026-09-02)

> **단일 출처 · 상태: 승인(2026-09-02 사용자)** — 2차 개정(대안 B 채택). 열린 질문 둘(§9)은
> 모두 권고안으로 결정됐다: 「건너뛰기」로 나간 날은 「안 썼다」로 기록 · 계단 둘로 나눠 출시.
>
> 근거: 실기기 사용 피드백(2026-09-02, 원문) — 「로션, 클렌징폼같은건 매일 사용하는데, 팩같은건
> 일주일에 한두번이란 말이지. 근데 지금 서비스는 모든걸 매일 사용한다고 가정하는거 같아.」
> 1차 초안은 빈도 필드만(A)을 권했고, 사용자가 **B(실사용 로그)를 택했다**(2026-09-02, 원문):
> 「B로 가자. B로 가면 사용 안했을 때 사진을 찍어도 그 사진의 의미가 부여돼. 단순 빈도로 가면
> 기록의 신뢰도가 떨어진다고 판단했어.」
> 이 문서는 [v1 설계](2026-08-29-v1-design.md)의 제품 스키마·촬영 화면·타임랩스 절과
> [서버 설계](2026-08-30-server-design.md) §4-2(블롭 화이트리스트)를 덮어쓴다.
> 직전 계단은 [v4-1 첫 화면 설계](2026-09-02-products-first-design.md).

## 0. 결론 요약

**핵심 가치의 재정의.** 관찰의 단위는 「제품 사용 구간」이 아니라 **「그날 무엇을 썼나 / 안 썼나」와
그 사진의 대조**다. 팩을 안 한 날의 사진이 팩을 한 날의 사진에 대한 **대조군**이 된다 — 그래서
안 쓴 날의 사진에도 의미가 생기고, 빈도 하나로 뭉갠 기록은 그 대조를 못 만든다(사용자 판단).
이 앱이 답하려는 질문은 「무엇을 쓰는 동안 달라졌나」에서 **「이걸 쓴 다음 얼굴과 안 쓴 다음 얼굴이
다른가」**로 한 단계 좁아진다.

- **로그는 사진의 속성이다.** 저장 단위는 `usage[사진 날짜] = 그 사진 직전 루틴(어제~촬영 전)에 쓴
  제품 id 배열`. 사진 날짜와 같은 키라 사진·관찰·로그의 대조가 **문자열 비교 하나**로 끝나고, 「팩은
  밤에 하고 사진은 아침에 찍는다」는 시점 불일치가 **정의로 해소**된다(§3-2).
- **묻는 자리는 촬영 직후 관찰 1문항 화면, 같은 스텝**이다. 관찰 질문 위에 「가끔」 제품 칩이
  토글로 서고, 관찰 답이나 건너뛰기를 누르는 순간 칩 상태가 통째로 저장된다 — **탭 수 증가 0**
  (안 쓴 날) 또는 쓴 제품 수만큼(§3-1). 「가끔」 제품이 없는 사용자는 **화면이 한 글자도 안 바뀐다.**
- **매일 제품은 로그를 안 받는다.** 매일 쓰는 제품은 구간 안에 대조군이 없어 로그가 관찰에 보태는
  것이 없고, 매일 n개 체크는 촬영 루프를 죽인다. 그래서 1차 초안의 빈도 필드가 **로그 대상을 고르는
  스위치**로 살아남는다: `frequency: 'daily' | 'occasional'`(매일 / 가끔) — A+B가 권고안이다(§3-5).
- **3상은 배열의 유무로 표현한다.** 키 없음 = 기록 없음(안 물어봄) · `[]` = 물어봤고 안 썼다 ·
  `[id…]` = 썼다. 칩이 눈앞에 있었던 날은 체크 안 된 것을 「안 썼다」로 **기록한다**(§3-4).
- **저장소는 관찰과 같은 꼴의 날짜 키 최상위 저장소** `facefit.usage`. 백업 블롭에 최상위 키
  `usage`가 하나 늘어 **서버 화이트리스트 변경이 필요하다** — 서버 PR을 먼저 배포한다(§4-1·§7).
- **계단 둘로 쪼갠다.** 계단 1 = 저장·백업·폼 어휘·촬영 스텝·카드 「n회」·타임랩스 프레임 배지.
  계단 2 = 타임랩스 바의 사용일 점 · 기록 캘린더 날짜 시트에서 보기·고치기(§7).
- 소급 입력 규율은 **관찰(그날의 눈)**에만 남고, 사용 로그는 **사실**이라 나중에 고칠 수 있다 —
  다만 그 입구(기록 시트)는 계단 2다. 계단 1에서는 「다시 찍기」가 곧 같은 날 정정 경로다(§3-3).

## 1. 문제 정의 (코드 실측 — 1차와 동일, 요지만)

제품 모델 `{ id, name, category, startDate, endDate?, mfds? }`에는 빈도도 사용일도 없다. 구간 = 매일
사용이 모든 화면의 암묵 전제다. 새는 표면 셋: ① 제품 카드 「n일째」(횟수로 읽힘) ② 타임랩스 구간 바
(꽉 찬 띠 = 매일) ③ 오늘 탭 「쓰는 중」(루틴에 있다는 뜻이라 왜곡 약함). `History`·`FacePhoto`·
`Restore`·`Onboarding`은 제품 표면 자체가 없다(DayCard는 `products`를 받지도 않는다).

B가 답하는 것은 이 셋의 **표시**가 아니라 **사진 한 장의 의미**다 — 「이 얼굴은 팩을 한 다음인가,
안 한 다음인가」. 그 답이 붙어야 타임랩스에서 대조가 성립한다.

---

## 2. 목표 · 비목표

**목표**: 가끔 쓰는 제품에 대해, **사진마다** 「그 전에 썼나 / 안 썼나」가 남는다. 매일 촬영 루프의 탭
수는 안 쓴 날 기준 **0 증가**. 서버가 죽어도 로그는 로컬에 남고 앱은 그대로 돈다(무음 폴백 규율).

**비목표(이번에 안 한다 — §8)**:
- 매일 제품의 로그. 구간 = 매일이 그 제품의 사실 선언이고, 대조군이 없어 관찰에 보태는 것이 없다.
- 사용 횟수 추정. 카드의 「n회」는 **기록된 사진 날짜 수**이지 실제 사용 횟수가 아니다(§4-5).
- 사진이 없는 날의 로그(저녁에 「오늘 팩 했다」를 적기). 로그가 사진의 속성이라 붙일 사진이 없다 —
  다음 날 아침 사진의 칩이 그 자리다.
- 오늘 탭·홈 칩 변경. 「쓰는 중」은 루틴 소속이라 그대로 참이다.
- 로그의 통계·요약(「팩 한 다음날 좋아짐 3/5」). 판단은 타임랩스를 보는 사용자의 눈이 한다(컨셉 §5-3).

## 3. 걸림돌 넷 → 설계 결정

1차 초안이 B를 기각하며 짚은 넷을 각각 푼다.

### 3-1. 매일 조작 추가 → 관찰 화면에 칩을 얹고, 제출은 기존 버튼이 겸한다

| 후보 | 매일 탭 수(안 쓴 날 / 쓴 날) | 판정 |
|---|---|---|
| **관찰 1문항 화면에 칩 추가(같은 스텝)** | **0 / 쓴 제품 수** | ✅ 채택. 관찰 답·건너뛰기가 이미 「이 화면을 나간다」는 버튼이라 제출 버튼이 새로 안 생긴다 |
| 관찰 뒤 별도 스텝 | 1(「없어요」) / 1+n | 기각 — 안 쓴 날이 대다수인데 그 날마다 한 탭 |
| 오늘 탭 「쓰는 중」 칩 토글 | 0 / n + 탭 이동 | 기각 — 촬영 동선 밖이라 잊는다. 로그가 사진의 속성(§3-2)이라 저녁 탭이 「오늘 아침 사진」에 붙는 것도 뜻이 어긋난다 |
| 제품 카드 「오늘 썼어요」 | 0 / n + 탭 이동 | 기각 — v4-1 「카드 안에 버튼은 없다」 규율 + 같은 시점 문제 |

**기본값이 조작을 0으로 만든다**: 칩은 **가끔(`occasional`) 제품 중 오늘 사용 중인 것**만 서고
기본은 전부 해제다. 매일 제품은 칩 자체가 없다(§3-5). 가끔 제품이 0개면 블록이 아예 안 그려지고
`onUsage`도 안 불린다 — 지금 사용자 대부분의 화면은 **0 변경**이다.

**건너뛰기의 뜻**: 관찰 건너뛰기는 여전히 「관찰을 기록하지 않는다」. 하지만 칩 블록이 떠 있었던
화면을 어떤 버튼으로 나가든 **칩 상태는 저장된다**(체크 없음 = `[]`). 이유는 §3-4.

### 3-2. 아침 촬영 ↔ 밤 팩 → 로그 날짜 = 사진 날짜, 뜻 = 「이 사진 직전 루틴에 쓴 것」

두 정의를 비교했다.

| 정의 | 촬영 화면 질문 | 사진과의 정렬 | 문제 |
|---|---|---|---|
| 달력 날짜(팩을 한 날) | 「**어제** 쓴 것?」 → 어제 키에 저장 | 사진 D ↔ 로그 D−1 | 아침 세안 전 쓰는 제품(주 1회 각질 세안)이 어제로 잘못 들어간다 · 캘린더·타임랩스마다 「하루 당기기」 규칙이 따라다닌다 |
| **사진 날짜(이 사진 직전 루틴)** | 「**어제부터 지금까지** 쓴 게 있나요?」 → 오늘 키 | **같은 키** | 화요일 밤 팩이 수요일 칸에 선다 — 시트·배지 문구가 「이 사진 전에 쓴 것」이라 말해 준다 |

✅ **사진 날짜**를 택한다. 사용자 발화가 정확히 「사진의 의미」였고, 정렬 규칙이 0개다(사진·관찰·로그가
같은 `YYYY-MM-DD` 키 — `logic/products.ts` 머리말의 문자열 비교 규율 그대로). 창은 **「어제부터 지금까지」**로
고정한다 — 하루 1장 리듬에 맞는 창이고, 며칠 걸렀다면 3일 전 팩은 「어제부터」에 안 들어가 체크되지 않는다
(효과가 빠진 사진이라 안 붙는 게 맞다).

### 3-3. 소급 규율 → 관찰은 그날의 눈, 로그는 사실. 사실은 고칠 수 있다

관찰 소급 금지(설계 §1-1)의 근거는 「피부 판단은 그날의 눈으로만 성립한다」다. 사용 로그는
「했다/안 했다」라는 **사실**이라 그 근거가 적용되지 않는다. 대신 다른 근거가 있다: 아침 촬영 직후의
급한 손이 칩을 빠뜨리는 것이 이 기록의 **주된 오류 모드**이고, 그걸 못 고치면 「기록의 신뢰도」(사용자가
B를 고른 이유)가 거기서 깎인다.

- **허용 범위: 사진이 있는 날 전부**(사진이 없는 날은 붙일 사진이 없다 — 비목표). 상한을 「어제까지」로
  두는 안은 기각 — 사실 정정에 기한을 두는 논리가 없고, 코드가 한 줄 늘 뿐 지키는 것이 없다.
- **입구는 둘, 계단이 다르다**: ① 같은 날 「다시 찍기」 → 촬영 스텝이 오늘 로그로 **미리 채워져** 뜬다
  (계단 1 — 「하루 1장, 다시 찍으면 덮어쓴다」 규율의 자연 연장) ② 기록 캘린더 날짜 시트에서 그날 칩을
  토글(계단 2). 관찰 답 칸은 시트에서 여전히 **읽기 전용**이다 — 규율은 갈라져 남는다.

### 3-4. 빠진 로그 vs 안 쓴 날 → 3상은 배열의 유무로, 「기록 열림」 = 칩이 떠 있었다

| 상태 | 저장 | 뜻 | 언제 생기나 |
|---|---|---|---|
| 기록 없음 | `usage[date]` 키 없음 | 안 물어봤다 | 가끔 제품이 하나도 없던 날 · 이 기능 이전의 사진 · 사진 없는 날 |
| 안 썼다 | `usage[date] = []` | 물어봤고 체크 없음 | 칩 블록이 떴고 아무것도 안 누른 채 나갔다 |
| 썼다 | `usage[date] = ['id…']` | 체크한 것 | |

별도 「열림」 플래그를 안 두는 이유: 빈 배열이 그 플래그다(필드 하나 덜). 「기록 열림」의 정의는
**칩 블록이 렌더됐다**이고, 그 조건은 코드로 하나다(가끔 제품 ∩ 오늘 사용 중 ≥ 1).

셋을 다르게 그리는 자리는 **타임랩스 프레임 배지**(계단 1)다: 썼다 → `8월 3일 · 팩` · 안 썼다 →
`8월 3일 · 쓴 것 없음` · 기록 없음 → `8월 3일`. 바의 점(계단 2)은 「썼다」만 찍는다 — 나머지 둘의 구별은
배지가 이미 하므로 바에 빈 점을 더 그리지 않는다(§4-8).

⚠️ 남는 위험: 급하게 「건너뛰기」를 누른 날이 「안 썼다」로 남는다. 「없어요」 버튼을 따로 두면 매일 한 탭이
늘어 §3-1이 무너진다. 정정 입구(§3-3)가 이 위험의 보상이다 — 사용자 확인 §9-1.

### 3-5. 매일 제품은 로그 밖 → 빈도 필드가 로그 대상을 고른다 (A+B)

`frequency: 'daily' | 'occasional'`, 없으면 `daily`. 1차 초안의 `'weekly'`(「주 1~2회」)를 버리는 이유:
로그가 있으면 「주 몇 회」라는 **선언**은 필요 없고, 이 필드가 하는 일은 하나 — **촬영 때 물어볼 제품인가**.
라벨은 「매일」 / 「가끔」이고, 「가끔」을 고르면 폼 아래에 한 줄이 선다: 「촬영할 때 이 제품을 썼는지 물어봐요」.

## 4. 명세 (구현자용)

### 4-1. 스키마 · 백업 · 서버

**결정: 날짜 키 최상위 저장소** `facefit.usage: { [date]: string[] }`. 제품 안 `usedOn: string[]`을 기각한
이유: 「물어봤고 안 썼다」(`[]`)가 날짜 단위의 사실이라 제품 안에 둘 수 없다 — 같은 정보를 두려면 결국
날짜 키 집합이 하나 더 필요해져 두 곳이 된다.

**백업 블롭**: 최상위 키 **다섯**(`schemaVersion` · `products` · `notes` · `usage` · `clientSavedAt`).
`schemaVersion`은 **1 유지** — `usage`는 선택 키이고, 2로 올리면 옛 빌드 클라의 `isBackupBlob`이 새 백업을
「없음」으로 읽는다(얻는 것 없이 잃기만).

| 한도(실측) | `usage`의 관계 |
|---|---|
| 최상위 화이트리스트(`BlobValidator.ALLOWED_TOP_LEVEL` 넷 · 모르는 키 400) | **`usage` 추가 필수** — 서버 변경 없이는 새 클라의 PUT이 전부 400 |
| 512KB 본문 | 하루 ~40B(`"2026-09-02":["id"]`) × 365 ≈ 15KB/년 — 여유 |
| 2,000자 재귀 문자열 상한 | id는 36자 · 날짜 10자 — 무관. 사진 불변식 그대로 |
| `MAX_NOTES` 4,000키 | **`MAX_USAGE_DAYS = 4_000`을 같은 논리로**(하루 1키 · 10년치) |
| `products` 200건 | 무관 |
| payload MEDIUMTEXT · 원본 바이트 저장 | 무관 — 서버는 `usage` 내부를 해석하지 않는다 |

**서버 변경 범위**(`server/src/main/java/com/facefit/backup/BlobValidator.java` 한 파일):
`ALLOWED_TOP_LEVEL`에 `"usage"` · `MAX_USAGE_DAYS = 4_000` · `usage`가 있으면 객체인지 + 키 수 검사

**배포 순서: 서버 먼저.** 새 클라 → 옛 서버는 PUT 400 → `backupDirty`만 서고 다음 앱 시작이 재시도한다

**클라 백업 코드**:

- `App.applyRestore`: `saveUsageAll(blob.usage ?? {})` 후 `loadUsage()`로 되읽기 — 복원은 덮어쓰기라 옛 백업이면 **비운다**.
- `Restore.tsx` 미리보기 문구는 그대로(「제품 n건 · 관찰 n건」) — 로그 건수는 사용자가 복원을 고르는 데 필요한 정보가 아니다.

### 4-2. `storage.ts`

```ts
export const FREQUENCIES = ['daily', 'occasional'] as const;
export type Frequency = (typeof FREQUENCIES)[number];
export const FREQUENCY_KO: Record<Frequency, string> = { daily: '매일', occasional: '가끔' };

export type Product = { /* 기존 */ frequency?: Frequency /* 없으면 daily. 촬영 때 물어볼 제품인가 — 구간 판정은 안 본다 */ };

/** 사진 날짜 → 그 사진 직전 루틴에 쓴 제품 id. `[]`는 「물어봤고 없음」, 키 없음은 「안 물어봄」 — 셋이 다르다. */
export type Usage = Record<string, string[]>;
export function loadUsage(storage = localStorage): Usage;                       // 객체 아님 → {} · 날짜 키 아님 → 그 키 버림 · 배열 아님 → 그 키 버림 · 문자열 아닌 원소 → 원소만 버림
export function saveUsage(date: string, ids: string[], storage = localStorage): Usage;   // notes의 saveNote와 동형 — 다음 상태를 돌려준다
export function saveUsageAll(usage: Usage, storage = localStorage): void;      // 복원 전용 — saveNotes와 동형
```
`reviveProduct`: `frequency`가 어휘 밖이면 **필드만** 지운다(`category`·`mfds`급 표시용 방어).
제품 id의 존재 여부는 로더가 **검사하지 않는다** — 지운 제품의 id가 남는 것이 정상이고(§4-9), 화면의 조인이 걸러낸다.

## 6. 리스크 · 판단 근거

- **관찰 화면이 두 질문을 진다.** 칩 블록은 가끔 제품이 있을 때만 서고, 제출 버튼은 그대로 셋+건너뛰기다.
  실기기에서 「무엇을 눌러야 나가는지」가 흐려지면 칩 블록을 접은 한 줄(「쓴 게 있나요? ▸」)로 바꾼다 — 이번엔 안 한다.
- **건너뛰기 = 안 썼다**(§3-4). 오답 위험은 정정 입구(같은 날 다시 찍기 · 계단 2 시트)로 보상한다. §9-1.
- **서버 배포 순서**를 어기면 새 클라의 백업이 400으로 밀린다 — 손실은 없고 재시도로 회복되지만, 사용자가 주황 「아직 백업하지 못했어요」를
  본다. 순서를 PR 본문·plan에 박는다.
- **`usage`가 백업에 실린다** — 제품 id와 날짜뿐이라 사진 불변식·2,000자 상한과 무관하다. 온보딩 백업 고지(「제품과 관찰」)에
  「사용 기록」이 들어가야 참이 되는지 릴리스 전 문구를 본다(§4-7).
- **카드 「n회」가 실제 횟수보다 작을 수 있다**(안 찍은 날의 사용은 없다). 라벨을 「회」로 두되, 오독 보고가 오면 「기록 n회」로 바꾼다(글자 하나).
- **유령 id**(지운 제품)가 `usage`에 남는다 — 화면엔 안 보이고 크기도 무해(§4-9). 
- **FacePhoto 테스트 파일이 이미 1,000줄급**이다 — 새 케이스는 「저장 직후 관찰 1문항」 describe 옆에 별도 describe로 붙여 setup을 공유한다.
