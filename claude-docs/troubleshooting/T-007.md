summary: GitHub OIDC의 `sub` 클레임이 레포마다 형식이 다르다(신규 레포는 `owner@id/repo@id`) — 옆 프로젝트의 IAM 신뢰 정책을 복사하면 「Not authorized」로 죽는다. 실제 클레임은 CloudTrail에서 확인한다

# T-007 · OIDC 신뢰 정책을 옆 레포에서 복사하면 안 된다 — `sub` 형식이 레포마다 다르다

- **증상**: facefit의 첫 배포가 `Configure AWS credentials (OIDC)` 단계에서
  `Not authorized to perform sts:AssumeRoleWithWebIdentity`로 12번 재시도 끝에 실패했다.
  신뢰 정책·OIDC 공급자·audience·역할 ARN·시크릿을 다 되읽어도 **전부 맞아 보였다**.
  같은 AWS 계정의 BookTimer는 **글자만 다른 같은 형식의 정책으로 몇 분 전에 성공**했다.

- **원인**: 신뢰 정책의 `sub` 패턴을 BookTimer 것에서 복사해
  `repo:Goospel/facefit:*`로 썼는데, GitHub이 facefit에 발급한 토큰의 실제 `sub`는
  **`repo:Goospel@80618017/facefit@1350348409:ref:refs/heads/main`**이었다 —
  소유자·레포의 **숫자 ID가 박힌 형식**이다. 같은 계정·같은 날인데 두 레포의 형식이 달랐다
  (booktimer는 `repo:Goospel/booktimer:ref:refs/heads/main`). GitHub이 이 형식으로 점진
  전환 중이고, **나중에 만든 레포가 새 형식을 받은** 것으로 보인다.
  에러 메시지는 어느 조건이 안 맞았는지 전혀 알려주지 않는다(의도된 설계다 — 열거 방지).

- **해결**: **CloudTrail Event history에서 실패한 `AssumeRoleWithWebIdentity` 이벤트를 찾아
  `userIdentity.userName`에 그대로 찍힌 실제 `sub`를 읽었다.** 그다음 신뢰 정책의
  `StringLike`를 배열로 바꿔 두 형식을 다 허용했다:
  ```json
  "token.actions.githubusercontent.com:sub": [
    "repo:Goospel@80618017/facefit@1350348409:*",
    "repo:Goospel/facefit:*"
  ]
  ```

- **재발방지**: ① **다른 레포의 신뢰 정책을 복사하지 않는다.** 형식이 레포마다 다를 수 있다.
  ② OIDC assume가 거부되면 **추측하지 말고 CloudTrail을 먼저 연다** — 실패 이벤트에 실제
  클레임이 남으므로 한 번의 조회로 끝난다(워크플로에 디버그 스텝을 넣고 재실행하는 것보다 싸다).
  ③ ⚠️ **BookTimer의 역할은 아직 옛 형식만 신뢰한다** — GitHub이 그 레포도 새 형식으로
  바꾸는 순간 배포가 멈춘다. 같은 방식으로 두 형식을 다 넣어 두는 것이 예방이다.
