# T-018 · 테스트 수가 줄어든 초록불 — vitest forks 풀 워커 타임아웃

- **증상**: 이 워크트리에서 `npm test`(= `vitest run`)를 처음 돌리니
  `[vitest-pool]: Failed to start forks worker for test files …` /
  `[vitest-pool-runner]: Timeout waiting for worker to respond`가 파일마다 떴다.
  결과 줄은 `Test Files 4 failed | 11 passed (15)` · `Tests 5 failed | 285 passed (290)` —
  **테스트 파일 25개 중 15개만 실행됐는데** 리포트는 그 15개 기준으로 정상 형태였다.
  기준선이 572건인 줄 알고 있지 않았으면 「290건 통과」를 전체 통과로 읽었을 것이다.

- **원인**: vitest 4의 기본 풀은 `forks`(자식 프로세스)다. 이 머신에서 워크트리를 새로 파고
  `npm install` 직후처럼 부하가 얹힌 상태로 25개 파일을 동시에 포크하면, 일부 워커가 제한 시간
  안에 응답을 못 해 **그 파일들이 실행조차 안 된 채** 「파일 실패」로 집계된다. 원인은
  테스트 코드가 아니라 프로세스 기동이라, 스택트레이스는 전부 vitest 내부만 가리킨다.

- **해결**: `npx vitest run --pool=threads`로 돌리면 25/25 파일이 다 뜬다(628건 통과).
  ⚠️ **재시도만으로는 안 정해진다** — 같은 `forks`로 두 번째 돌렸을 때도 시간이 걸리는 만큼
  다른 파일이 타임아웃될 수 있다. 풀을 바꾸는 것이 유일하게 결정적인 조치였다.

- **재발방지**: ① **테스트 결과는 통과/실패가 아니라 「몇 건 돌았나」로 먼저 읽는다.**
  기준선 수(이 시점 572건)를 알고 시작하고, 총계가 줄었으면 초록·빨강과 무관하게 실행 자체를
  의심한다 — 「관측 경로를 먼저 의심한다」(글로벌 브라우저 절)의 테스트판이다.
  ② 이 레포에서 전체 통과를 근거로 삼을 때는 `npx vitest run --pool=threads`를 쓴다.
  `npm test`의 기본값은 그대로 둔다 — CI·다른 머신에서까지 풀을 못 박을 근거는 아직 없다.
  ③ 「무성 실패」 가족이다(T-014 ③) — 이번엔 에러가 **있었는데도** 총계가 그럴듯해서 위험했다.
  에러 메시지가 아니라 **표본 수**가 신호였다.
