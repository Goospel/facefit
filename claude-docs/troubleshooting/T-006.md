# T-006 · SSM 명령 JSON에 한글을 넣으면 AWS CLI가 못 읽는다

- **증상**: EC2에 진단 명령을 보내려고 `aws ssm send-command --parameters file://ssm.json`을 쳤는데
  `Error parsing parameter '--parameters': Unable to load paramfile (...), text contents could not be
  decoded. If this is a binary file, please use the fileb:// prefix instead`로 즉시 실패했다.
  파일은 정상 UTF-8이고 JSON 문법도 맞았다. 앞서 같은 방식으로 보낸 명령들은 잘 돌았다 —
  **다른 점은 이번 것의 `echo` 구분선에 한글이 섞였다는 것뿐**이었다.
  이어서 `CommandId`가 빈 문자열이 되어 뒤따르는 `wait`·`get-command-invocation`까지
  「Invalid length for parameter CommandId」로 연쇄 실패해, 원인이 더 가려졌다.

- **원인**: Git Bash 히어독은 UTF-8 바이트로 파일을 쓰는데, Windows의 AWS CLI는 `file://`
  페이로드를 **시스템 로케일(CP949)**로 디코딩한다. 한글 UTF-8 바이트가 CP949로 해석되지 않아
  파일 로드 단계에서 죽는다. 「Windows 셸 한글·인코딩 원칙」의 SSM 판이다 —
  파일 경유로 우회하는 습관(T-026 커밋 메시지)이 여기서는 **오히려 함정**인 셈이다.

- **해결**: 원격 명령 문자열을 **ASCII로만** 썼다. 구분선을 `echo '=== caddy networks ==='`처럼
  영문으로 바꾸자 그대로 통과했다. 명령의 *출력*에 한글이 섞이는 것은 무관하다 —
  문제는 CLI가 읽는 **입력 파일**뿐이다.

- **재발방지**: **`aws ssm send-command`에 넘기는 JSON에는 한글을 쓰지 않는다.** 설명이 필요하면
  `--comment`가 아니라 코드 주석이나 문서에 남긴다. 그리고 이 실패는 `CommandId`를 빈 값으로
  만들어 **다음 두세 명령까지 엉뚱한 에러로 연쇄**시키므로, 파이프라인 중간의
  「Invalid length for parameter CommandId」를 보면 앞선 `send-command`의 실패를 먼저 의심한다.
