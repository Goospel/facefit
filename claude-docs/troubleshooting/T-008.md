# T-008 · mysqldump를 잘라서 복원하면 한글이 깨진다 (그리고 그게 백업 탓으로 보인다)

- **증상**: 백업 복구 리허설에서 `--databases booktimer facefit` 덤프의 **facefit 구간만**
  `awk`로 뽑아 스크래치 DB에 복원했더니, 행 수는 맞는데(2/2) **payload의 한글이 깨졌고**
  라이브 데이터와 불일치(`payload_identical=0`)로 나왔다. 마지막에
  `ERROR 1231: Variable 'time_zone' can't be set to the value of 'NULL'`도 났다.
  잠깐 **백업이 깨졌다고 오해**했다 — 백업 서비스의 백업이 못 믿을 것이라는 최악의 결론이다.

- **원인**: 잘라낸 것은 데이터가 아니라 **덤프의 머리와 꼬리**였다. mysqldump는 파일 맨 앞에
  `/*!40101 SET NAMES utf8mb4 */`와 `SET @OLD_TIME_ZONE=@@TIME_ZONE` 같은 세션 설정을 넣고,
  맨 뒤에서 그것을 되돌린다. 중간 구간만 넘기면 ① 클라이언트가 기본 문자셋으로 읽어 UTF-8
  바이트가 재해석되고(한글 깨짐) ② 꼬리의 `SET TIME_ZONE=@OLD_TIME_ZONE`이 NULL을 받는다.
  **데이터는 멀쩡한데 복원 방법이 망가뜨린 것**이라, 증상이 백업 실패와 구별되지 않는다.

- **해결**: 덤프를 **수정 없이 통째로** 빈 MySQL에 복원했다. 운영 박스에 두 번째 MySQL을
  띄우는 대신 **로컬 Docker**로 했다(`docker run --rm mysql:8.4`) — 같은 산출물이고 운영
  위험이 0이며, 실제 재해 복구 절차(새 박스 + 빈 MySQL)와도 같은 모양이다.
  결과: rc=0 · 두 DB 복원 · 한글 보존 · **라이브 API 응답과 바이트 단위 동일**.

- **재발방지**: **복구 리허설은 덤프를 자르지 않는다.** 한 DB만 필요하면 구간을 뽑는 대신
  통째로 복원한 뒤 그 DB만 본다. 운영 DB를 덮어쓸까 봐 자르고 싶어지는데, 그 걱정의 답은
  「자르기」가 아니라 **「격리된 빈 MySQL에 넣기」**다. 그리고 리허설에서 데이터가 이상해
  보이면 **백업보다 복원 절차를 먼저 의심한다** — 덤프는 자기 설정을 헤더에 들고 다닌다.
