# T-014 · 쓰기의 성공 응답은 반영의 증거가 아니다

- **증상**: 콘솔 상세 설명의 「'오늘' 탭에서 기록 백업을 켜면」이 (백업을 「제품」 탭으로
  옮기며) 거짓이 돼서 `miniapp_update_basic_info`로 고쳤다. 응답은
  `{"miniAppId":70438,"appName":null}` — **에러가 없다.** 그런데 `miniapp_get`은 **옛 문구
  그대로**였고 `miniapp_meta_status`의 `reviewState`도 `APPROVED`에서 안 움직였다
  (앱정보를 실제로 고쳤다면 검토 대기로 갔어야 한다).

- **원인**: 미상. 재현 경로도 못 잡았다 — 알아낸 것은 **이 tool의 성공 응답이 반영을
  보장하지 않는다**는 사실 하나뿐이다. 응답에 바뀐 값이 안 실려 오는 형태
  (`appName: null`)라 응답만 봐서는 애초에 판별할 수단이 없다.

- **해결**: 고치지 못했다. `review_submit`은 반려·재검토용이라 `APPROVED` 상태에서 쓰면
  앱정보를 **불필요하게 검토 대기로 돌린다** — 그래서 재시도 대신 **사용자에게 보고**했고,
  사용자가 출시하러 콘솔 웹에 들어간 김에 두 글자를 고쳤다. 검수 리스크는 낮았다:
  개인정보 문장(사진은 기기에만·제품과 관찰만 서버로·끄면 삭제)은 전부 여전히 참이었고,
  릴리스 노트가 「'제품' 탭 맨 아래」라고 적어 검수자를 옳은 자리로 보냈다.

- **재발방지**: ① **외부 시스템에 쓴 뒤에는 되읽어 확인한다** — 특히 응답에 반영된 값이
  안 실려 오는 API는 성공/실패 코드가 유일한 신호라 무성 실패를 못 거른다.
  ② 이 프로젝트에서는 `miniapp_update_*` 계열을 부를 때마다 `miniapp_get`으로 대조한다.
  안 바뀌었으면 **재시도하지 말고 콘솔 웹**으로 간다 — 실패 원인을 모르는 채 재시도하면
  같은 no-op을 반복하거나, 우회로(`review_submit`)로 멀쩡한 상태를 망친다.
  ③ 「무성 실패」 가족이다 — Git Bash grep(멀티바이트 0건)·번들 문자열 grep과 같은 부류로,
  **에러가 없다는 것은 아무 증거도 아니다.**
